# AGENTS.md — EO1 / EO2 Immich frame APK

## Goal

Android home-screen replacement APK for Electric Objects **EO1** and **EO2** digital frames. It rotates photos and videos on an interval so display never depends on Electric Objects’ cloud; the assets come from files uploaded to the frame's own LAN web server (`{"type":"local"` backend), a self-hosted [Immich](https://immich.app/) server, or both.

- Package ID: `com.aphex3k.eo1`
- Product source: `app/` (Java Android module)
- Human ops guide: [README.md](README.md); install / hardware bootstrap: [docs/SETUP.md](docs/SETUP.md)
- Hardware notes: [EO1-specs.md](EO1-specs.md)

## Tech stack & hard constraints

- **Language:** Java only — no Kotlin
- **SDK:** `minSdk` / `targetSdk` / `maxSdk` = **19** (KitKat 4.4.2); `compileSdk` 34
- **Build:** Gradle + Android Gradle Plugin; all builds are local (the old Jenkins CI is gone — `publish-update.sh` at the repo root builds + signs release APKs via `local.properties` signing props). Every build also carries its own provenance: `BUILD_DATE` (the commit timestamp), `GIT_SHA` and `GIT_DIRTY` as `BuildConfig` fields, generated **lazily** through `androidComponents.onVariants` + `providers.provider` — never a configuration-time `new Date()`, which rewrites `BuildConfig.java` and recompiles the whole module on every Gradle invocation, `test` included (AGP 8.x has no lazy `buildConfigField` overload; the variant `buildConfigFields` map does). `com.aphex3k.eo1.BuildFacts` renders it in one place for the options dialog's read-only **About** tab, `/state`'s `app` block and the web page header — without it a release build says nothing about itself on screen, since the version overlay is `BuildConfig.DEBUG`-gated. `BuildFacts` reads the installed signing certificate the same API-19 way `UpdateManager.installedCert()` does (`PackageInfo.signatures`, never `signingInfo`, which is `NoSuchFieldError` on KitKat); `BuildFacts.RELEASE_CERT_SHA256` is the expected release fingerprint the verdict line compares against — public data from `keytool -list -v -keystore <release.jks>`, to be re-read whenever the keystore rotates, and left blank means "not checked", never "mismatch".
- **Crash diagnostics:** release is R8-minified (`minifyEnabled = true`, and `proguard-rules.pro` keeps `SourceFile,LineNumberTable`), so a release trace is unreadable without the build's `mapping.txt`. `publish-update.sh` therefore archives it as `mapping-<VERSION_CODE>.txt.gz` beside the APK, and every crash report carries its `versionCode` in both file name and header — `versionCode → mapping` is 1:1 because the script enforces strictly increasing codes. The mapping is an archive for humans: it is deliberately **not** referenced in `update-manifest.json`, so no frame ever downloads it. If you disable minification you must still publish (or the escape hatch `EO1_UPDATE_MAPPING_OPTIONAL=1` makes the missing mapping loud instead of silent)
- **Networking:** Retrofit + OkHttp + Gson; hand-rolled Immich client; self-update via `com.aphex3k.update` (plain-HTTP manifest + pure-Java JAR signature verification + headless install). Headless install: `installPackage` reflectively when the app holds `INSTALL_PACKAGES`, otherwise the device's own adbd on `127.0.0.1:5555` (`AdbdInstallClient` speaks the minimal adb wire protocol and runs `pm install`; sideloaded frames lack the signature-level `INSTALL_PACKAGES` permission). **That protocol is fourcc-tagged messages, and the header's checksum word is a byte sum, not a CRC32** — both measured against a live daemon, because nothing negotiates them: tags travel as ASCII (`CNXN` = `0x4e584e43`, not the `0x0100000N` of old `adb.h`), and a CRC32 in the checksum field is answered with a closed socket. Before this was found the client emitted the `%04x`+`host:version` framing that belongs to the *host's* `adb server` on 5037, so adbd never saw a request and every `install`/`exec` reported `UNREACHABLE` after its read timeout — meaning the adbd transport had never worked on any frame, while `probe()` (a bare TCP connect) kept reporting `adbdReachable: true`. **Do not assume the ROM configured that adbd:** the EO2 ROM listens on TCP 5555 with `ro.adb.secure` unset, the EO1 ROM does not listen at all (`ECONNREFUSED`). The app may start it — `AdbdInstallClient.ensureTcpAdbd(allowed)` writes `service.adb.tcp.port=5555` + `ctl.restart=adbd`, rate-limited to one restart per 10 min — but **one action at a time and only when the operator enabled both `Trusted Network` and `Allow loopback ADB for update installs`** (`SettingsManager.isLoopbackAdbEnabled()`, both SharedPreferences-backed and default off), because TCP adb has no loopback-only mode and is reachable **as root** from anywhere routable. `teardownTcpAdbd()` (`port=-1` + restart) closes it in a `finally` the moment that install ends, so the exposure window is one install, never a boot; a daemon the ROM owns is never touched, and a note in the state file lets the next launch close a window an install's success left open. **Never arm it to be ready**: a `DeviceRepair` rung the watchdog has actually reached may start it for the duration of that one rung and closes it in the same `finally`, but the launch-time vendor `pm disable` only probes — adbd is never left listening because the app booted. An automatic cycle never shows the install-intent confirmation UI: a frame with no working silent transport leaves the update `STAGED` with `needsHumanConfirmation` set and says so in `/logs` + `/state` + the web page; the dialog appears only when the operator presses *Install on the frame* (never armed with the relaunch alarm, which used to fire the app back over a pending dialog)
- **Immich server:** supported band is the **whole 3.x line** (`3.0.0` up to, but excluding, `4.0.0`) — endpoints verified byte-identical through **3.3.3**. The band lives in `com.aphex3k.media.immich.ImmichClientRegistry` (the V3 client); each backend entry may pin its `apiVersion` (default `"auto"` = best-effort probe of `GET /api/server/version`). Ceilings sit on major boundaries, not on the last release someone checked: Immich marks its own stability in the spec (`x-immich-state`/`x-immich-history`) and defers removal of deprecated fields to the next major, so a 3.x minor cannot break a client that matched an earlier 3.x. A server **newer** than every known band is served best effort by the newest client and raises a one-shot compatibility warning through `MediaBackend.compatibilityWarning()` (toast + `/logs`) instead of being refused; a server **older** than the first band is still refused, because there we know the client speaks the wrong API. On a real breaking change, add a new frozen `com.aphex3k.immichApi.vN` DTO package + `ImmichClientVN` + one registry band; never edit a frozen client package. To re-verify the band cheaply, diff `open-api/immich-openapi-specs.json` in `immich-app/immich` between release tags for the operations this app calls (`ImmichApiService`) and the schemas they reference. **Authentication:** the configured `userid`/`password` pair is sent to `POST /api/auth/login` and nowhere else; that call's `accessToken` (a JWT — Immich's own session cookie carries the identical string, so there is no cookie jar in this app) is held in `com.aphex3k.media.immich.ImmichSessionStore`, one entry per host+user, attached as `Authorization: Bearer` by `ImmichAuthInterceptor` and reused across pool rebuilds and restarts. Immich 3.x has **no refresh endpoint**, so renewal is re-login, driven by the token's own `exp` claim (`JwtExpiry`) or by a 401 — never by re-sending credentials per request. The store is process-wide on purpose: `rebuildPool` news a backend per entry, and a client-owned session would mean a login per tick whenever the pool is failing. A failed login cools down for 60s rather than retrying; the token is mirrored in default SharedPreferences under `immich_sessions` and served by no web route.
- **TLS:** EO1 needs TLS 1.2 and weaker ciphers — see `Tls12SocketFactory.java` and `ApiServiceGenerator.java`. **Trust anchors are a separate problem from protocol**: the ROM's CA store is from about 2013 (measured on a live EO2: 156 anchors, 63 past their own `notAfter`, and **zero** Let's Encrypt/ISRG), so an Immich host on a current certificate cannot be validated by the device at all — which is why `ApiServiceGenerator.enableTls12OnPreLollipop` used to call `sc.init(null, null, null)` and now installs `com.aphex3k.eo1.trust.MergedTrust`'s manager instead: the platform's anchors enumerated at runtime, merged with `RootBundle`'s shipped roots. Three rules follow. (1) **Merging may only add.** If platform enumeration yields nothing, or the merged set is smaller than the platform's, the manager is not installed and the frame trusts what it trusted before — a narrowed set breaks hosts that work today and reports itself as a certificate problem. The same applies to the cipher list: `MODERN_TLS`' suites are kept and the two ECDSA-CBC ones are appended (this platform has no AEAD, so an ECDSA chain needs them named); *replacing* the list deletes TLS 1.2 GCM for every newer platform this code runs on, which is what the Immich live-tests caught. (2) **Roots are one of four gates** — anchors, ECDSA-CBC suites, server cipher policy, device clock (the app does no time sync, and LE lifetimes are 90 days) — so a fix must be reported as *which* gate it opens, not as a failed one. `/state`'s `trust` block names three of them (anchor counts + `missingBundleAnchors`, `gates.anyEcdsa`/`anyAead`/`supported`, `nowMs`); the one it cannot see is the **server's own cipher policy** (gate 3 of [docs/TRUST.md](docs/TRUST.md)), read instead from the failure's text (`handshake_failure` at `SSL23_GET_SERVER_HELLO`, before any certificate is looked at). `TrustCensus.classifyFailure` is that taxonomy in code, and `TrustCensus.gateNote` is how a frame reports it: appended to a backend's last-fetch record (the `backends:` line of the state dump and of a `Capture now` report) and to an update's `lastError`, which `/state` serves in its `update` block. It returns the empty string for a failure that is not about trust, and that is the half of the contract a future edit must not lose — a timeout carrying a `[TLS gate: ...]` suffix is what sends an operator reinstalling roots against a dead radio. The note belongs on the report, not in remembered state: a later healthy connection must not have to know to clear it. (3) **An app-local decision does not reach the kiosk WebView**: Chromium-33 validates in its own engine and ignores any Java trust manager, so an `https://` page still depends on the ROM store. Roots are shipped as generated compile-time constants (`./gen-root-bundle.sh` → `RootBundle.java`, inputs in `certs/roots/`) rather than `assets/`/`res/raw`, both because release builds set `shrinkResources = true` and because a store filename handed to a root shell must be knowable at build time; the switch is `trust_bundle` in default SharedPreferences, **on by default** (unlike `trusted_network`/`loopback_adb`, this grants no privilege — it trusts public roots that arrived inside an already-signature-verified APK). It has **no UI**: no options-dialog checkbox and no web route writes it (`SettingsManager.setTrustBundleEnabled` has no caller), so switching it off means editing `com.aphex3k.eo1_preferences.xml` from a root or `adb` shell — and `RootBundle` ships **10** roots, whose count `/state` reports as `trust.bundleSize`.
- **Video:** Prefer Amlogic **TsPlayer** (`TsVideoView` + `libTsPlayer-jni.so`) on Geniatech EO1/EO2 when the native library loads; **automatic fallback** to platform `MediaPlayer` via `com.dd.crop.TextureVideoView` — and routing to the fallback is forced for videos whose display-matrix rotation is non-identity, and for videos whose display aspect is opposite the frame's display orientation (the TsPlayer `.so` has no scale/rotation control; see docs/TSPLAYER.md "Scaling & orientation (routing)"). **Do not use ExoPlayer** (including 2.19.x / Media3) — it triggers MediaCodec/GPU driver lockups that hang the whole device (ADB dies; requires power-cycle). See [docs/TSPLAYER.md](docs/TSPLAYER.md).
- **Web pages ("kiosk web"):** `com.aphex3k.media.web.WebsiteBackend` puts a configured page URL into the rotation pool as a `MediaType.WEB` asset. It has no bytes: `MediaManager` never runs it through `acquireAsset`/cache/integrity, and hands the URL to `MainActivity.displayWebsite`, which renders it in a chrome-less platform `WebView` (no extra dependency, no `@JavascriptInterface` bridge). The view is created lazily on the first web asset and inserted above the image view — a frame with no web backend must never load a WebView provider, and every other display path must hide it again. Whether it *worked* is only known asynchronously, so failures bypass the `assetFallback`/`tagAssetAsIncompatible` path entirely: `onReceivedError` or a 30s load watchdog calls `MediaManager.webDisplayFailed`, which reveals the image underneath and advances to the next pool asset (capped per cycle). A ROM with no usable WebView provider must degrade to skipping web assets, never crash into `System.exit(2)`. The engine is Android 4.4's Chromium-33 WebView: expect LAN-hosted or deliberately legacy pages over `http://`, not modern SPAs.
- **No client-side transcoding / conversion:** The downloaded Immich original is used as-is — there is no on-device FFmpeg, video re-encode, or image resize. **Nothing in `fetchCatalog` filters on decodability, and no asset is judged by a file name that merely *could* hold a bad codec (`.mov`, `.mp4` are containers, not verdicts).** Every image and video the account can see joins the rotation pool (`ImmichMediaBackend.isDisplayable` checks media type and trash only), and each one is *displayed*: the original is always the first attempt, and a display failure moves one rung down a strict ladder — original → (video only, and only while `preferTsPlayer` is true) the same original on the other player engine → backend fallback (Immich `/thumbnail?size=preview` for stills, `/video/playback` for video) → flagged; a **local upload has no degraded source at all** (`MediaBackend.resolveThumbnailFallback` is the interface default returning null for `LocalMediaBackend`), so its ladder is one rung shorter and its last rung dead-ends. Only the last rung decides incompatibility, because metadata is the one thing that can be stale: an operator who regenerates thumbnails, or a server that upgrades its HEIF handling, gets the asset back into the rotation on the next pool rebuild with no app change and no tag to clear. Failing to *fetch* an original counts as that rung failing: `MediaManager` falls through to the degraded source instead of reporting the asset as an error, because the ladder — not the rotation loop — is what decides. The exception is a failure with a cause (an `IOException` from the wire): that is nobody's asset, it propagates, and a frame with no network must not spend a thousand thumbnail requests proving it. Three throughput/size gates route, and none of them ever drops or tags an asset: originals above `MAX_ASSET_BYTES` — **1 GiB** (`MediaManager.java:57`), a per-file ceiling and not a capacity claim: the ~800 MB figure elsewhere in this file is *total* app storage on this hardware, so what binds one download is the smaller of 1 GiB and the free space left after `MediaCacheManager.SAFETY_MARGIN_BYTES` (128 MB) —, videos with a coded side over 1920px (`MediaCompatibility.incompatibleVideoResolution`), and videos whose sustained macroblock throughput exceeds `MediaCompatibility.MAX_VIDEO_MACROBLOCKS_PER_SECOND` (`incompatibleVideoThroughput`, from coded size x frame rate). **All three choose a source, and therefore apply to remote backends only:** `MediaManager.originalUsable` returns true the moment `asset.localPath` is set (`MediaManager.java:913-926`), so an uploaded file is never routed around its own size, coded dimensions or frame rate — it is displayed at whatever it arrived as, in slow motion if the decoder cannot keep up. That is deliberate, not an oversight: a local upload has no degraded source to be routed *to*, so gating it would mean not showing it at all. The first two are decided from catalog metadata before any download. The third cannot be: no backend reports a frame rate, so it is judged from the `moov` of the original once it is on disk (`VideoHeaderProbe.StreamStats.fpsMilli`), which means the asset's first appearance pays one original fetch and then descends to the fallback inside that same acquisition — and every later acquisition of it starts at the fallback, because the verdict is remembered per asset key for the life of the process. All three exist for the same reason: that decoder fails *without raising an error*, so waiting for a failure would show garbage or slow motion forever and never reach the fallback. Throughput in particular must never reach `tagAssetAsIncompatible`/`knownIncompatibleKeys` — the clip is decodable, merely beyond the hardware, and a verdict that could not be undone by a later server-side transcode would be a lie about the user's library. If that transcode is later produced, the gate notices on its own, because the fallback is not fetched blindly: `ImmichMediaBackend.resolveThumbnailFallback` first asks the playback URL how big its answer would be (`Range: bytes=0-0`, total read from `Content-Range` on a 206 or `Content-Length` if the server ignored the range) and carries it as `MediaSource.expectedBytes`. When that equals the asset's own `sizeBytes` the server has nothing transcoded and the "degraded source" is a second copy of bytes already held — which cost a real 158 MB asset being fetched and cached twice at 0.18x — so `MediaManager` takes the original instead and records the asset as having no transcode, a mark that also stops the throughput verdict and the probe from re-triggering each other every cycle. A probe that cannot answer is read as "worth fetching", the direction that can never skip a fallback that would have worked — and because that is a heuristic rather than a proof, `acquireFallbackSource` compares the finished artifact's length against the asset's and deletes it when they match. A byte-identical fallback must never exist on the device, not merely be unlikely: it is double the bytes, and it competes with useful files for eviction on a device with about a gigabyte free. Deletion therefore covers both directions — one written now, and one left behind by an older build. The original is kept cached rather than discarded as the other verdicts do. Their fallback artifact is cached exactly like an original — same integrity gate, same `<name>.sha1` sidecar, under a distinct `<uuid>_fb.<ext>` cache name so it can never evict-match the original it stands in for. A leading-`ftyp` byte check still runs on downloaded originals (catches HEIF content named `.jpg`), and so does a video sample-description check through `VideoHeaderProbe` — the one place a `.mov`'s real codec is readable, since the container extension is a claim rather than a fact (catches HEVC/AV1/Dolby-Vision content named `.mov`, the everyday iPhone case). It runs on the degraded artifact too: a server with nothing transcoded answers `/video/playback` with the original bytes, and that last rung is now flagged instead of painted black. An asset whose bytes are verified undecodable is remembered for the life of the process so its original is not re-downloaded every rotation, and retried after a restart. Flagging writes the Immich `EO1_INCOMPATIBLE` tag through `MediaBackend.markIncompatible`, which runs on the manager's tagging thread and lets every failure propagate (`ImmichApiTagException` carries the server's status line); `MediaManager` reports it to `/logs` and `eo1-app.log`, never to logcat alone — a tag the server refused must not be indistinguishable from an asset that never needed one. That tag is **operator-facing only**: the app never reads it back as a filter, and re-tags an already-tagged asset on every double failure, so a fixed asset needs no app-side unfreezing and a stale tag cannot retire one. For local uploads, the failure the **scan-time** check sees is made durable — and only that one: `LocalMediaBackend.fetchCatalog` writes a plaintext sidecar report `<name>.incompat.txt` next to the file on first failure (`com.aphex3k.media.local.CompatibilitySidecar` — exact reason, user-actionable fix, JSON diagnostic block); while that sidecar exists the asset is excluded from the rotation pool, sidecars are never part of the rotation themselves (`.txt` is not a media extension), and both the asset and its report are listed/served/deletable through the web server's `/files/<name>` — the only sanctioned way to re-admit an asset is to delete its sidecar. **A failure at display time is a different event and records nothing durable for a local file**: `markIncompatible` is the interface default no-op that `LocalMediaBackend` never overrides, and the display path writes no sidecar (`writeIfAbsent` is called only from `fetchCatalog`), so the next cycle attempts the same bytes again. The dead end is barely even visible: `displayFallbackSource` logs "backend 'local' has no fallback" to **logcat only** — no `postDebugInformation`, so nothing reaches `/logs` or `eo1-app.log` (which is exactly why the difference matters at 3 a.m., when logcat holds ~13 minutes) — and `tagAssetAsIncompatible` then succeeds vacuously. The one in-process exception is `renderSilentVideoKeys`, which a restart forgets. Do not describe a display-time upload failure as reported, tagged or retired.
- **Video health is judged by pixels, not only by callbacks:** every other failure signal in the display path is a callback (`onError`, a throw in `onVideoPrepared`) or a *position* stall, and this decoder's documented failure mode is silent — bytes are accepted, `prepare` succeeds, the timeline advances, and nothing reaches the screen. So the MediaPlayer path supplies a real signal: `com.dd.crop.TextureVideoView.onSurfaceTextureUpdated` stamps the last composited frame (`VideoPlayerController.getLastFrameAtMs()`, `supportsPaintSignal()`; TsPlayer returns "no signal" because its `.so` offers nothing per-frame and its reported position is wall-clock when the native clock is unusable, so watching it would measure a timer). Three rules follow. (1) **A display attempt is armed with a paint deadline before any callback** (`MainActivity.startVideoPaintWatchdog`, `VIDEO_PAINT_TIMEOUT_MS`, mirroring the web path's `startWebLoadWatchdog`) so an attempt whose `prepareAsync()` never returns is still watched — the position watchdog cannot cover that case because it is armed *from* `onVideoPrepared`. While the panel is not ours to paint (quiet hours, `onPause`, the screen toggle) that poll **parks** instead of cancelling or spending its deadline, and `onResume`/`turnScreenOn` re-arm it with the parked time deducted and the video surface made visible again: a `TextureView` that is INVISIBLE composites nothing, so an unparked clock would sentence a healthy clip for the whole process on the strength of the app's own visibility bookkeeping. (2) **The photo is stepped aside only once a frame is proven to exist** (`revealVideoSurface`), never at prepare, and the ImageView is hidden rather than `Glide.clear`'d — clearing empties the drawable, and every recovery path reveals the photo by setting it VISIBLE, so clearing turned "restore the image underneath" into revealing an empty view over a black root. On an engine with no paint signal the hide stays at prepare. (3) **A confirmed no-pixels verdict skips and never tags**: a clip that reached the last rung and still rendered nothing goes into `MediaManager.renderSilentVideoKeys` (in-memory, per-process, forgotten on restart) and is shown as its `/thumbnail?size=preview` still instead of as a video, from `displayVideo`'s entry check onward — so later cycles never decode or display it, though acquisition still resolves its original normally (the skip lives on the display side, with the rest of the ladder). That verdict is deliberately **not** written to Immich: the fourcc tier states something about the file, this states only what this device's decoder did with it, and a wrongly-written `EO1_INCOMPATIBLE` outlives the frame that made it. The refusal is enforced inside `MediaManager.tagAssetAsIncompatible` (an asset in `renderSilentVideoKeys` is never tagged) rather than at the call site, because the substituted still re-enters the ladder's terminal rung — a preview the device cannot decode would otherwise reach the server through the one door the policy left open. When `preferTsPlayer` is false there is no second engine, so the `ORIGINAL_REPLAY` rung is skipped rather than replaying the same bytes through the same deterministic routing decision.
- **Secrets:** Immich password is stored cleartext in device `configuration.json` — never commit a real config

Do not casually bump SDK levels or modernize AndroidX / OkHttp / Retrofit; pins exist for API 19.

## Architecture / entry points

```
Eo1Application (manifest android:name)
  ├── CrashReporter         → the process's only UncaughtExceptionHandler, installed in attachBaseContext
  └── CrashSources          → startup scrape: `system` logcat buffer (API 19 has no `crash` buffer), /data/system/dropbox, /data/anr
  ── all of which write through CrashStore → filesDir/crashes (served by /crashes, /crash.json, /crash/<name>)

MainActivity
  ├── SettingsManager       → configuration.json (Configuration.java, backends list)
  ├── MediaManager          → com.aphex3k.media.MediaBackend (ImmichMediaBackend → ImmichClientV3 → com.aphex3k.immichApi | LocalMediaBackend | WebsiteBackend → kiosk WebView)
  ├── Video playback        → TsPlayer (preferred) / MediaPlayer fallback
  ├── BrightnessManager / BrightnessSensorManager
  ├── UpdateManager         → com.aphex3k.update (manifest-driven self-update: SHA-256 + JAR signature + cert match; headless install via installPackage, else adbd loopback `pm install` via AdbdInstallClient)
  └── KioskWatchdog         → self-recovery ladder on its own Timer thread (force rotation → redraw → Wi-Fi repair via DeviceRepair/adbd → self-restart → opt-in reboot), each exit of the reboot rung writing one diagnostics report first; see docs/WEBSERVER.md "Self-recovery" and "Diagnostics reports"
```

## Config

Device config lives at `/data/data/com.aphex3k.eo1/files/configuration.json`.

- Prefer **`Configuration.java`** as the source of truth for fields.
- `configuration_example.json` is a template for the new multi-backend shape — deliberately listing the `local` entry **first**, because that is the source that needs no server, no credentials and no certificate.

Current model fields: `backends` — a list of `ConfigurationBackendEntry` (`type` "immich"|"local"|"web", `id` like "immich-1"/"local"/"web-1", `host`, `userid`, `password`, `apiVersion` = "auto" or a pinned semver, and `enabled` — **true by default**, and an absent key means true so a config written before the flag existed keeps its backends active; `MediaManager.buildGeneration` skips a false entry and leaves it in the document, so turning a source off is reversible without editing it away. The trusted-network web config editor renders that checkbox for **immich and web** rows and deliberately renders **none** for a local row (the row reads "local uploads (files stored on this frame - no server, no login)"), because the local store has no failure to gate and no credentials to retire — but `enabled` is still honored on a hand-edited local entry, so it is the field name to know); local entries carry otherwise only `type`/`id`, at most one is honored, and **it must exist**: files uploaded through the web page land in `filesDir/uploaded` and are listed by `/files` whether or not a `local` entry is configured, but nothing joins them to the rotation without one — neither the upload handler nor `Configuration.normalize` creates that entry (normalize only assigns the `id` to a `local` entry already present, and dedupes a second one), and the page's *Add local uploads* button sits inside the trusted-network-gated config editor; a **web** entry carries only `type`/`id`/`host` and one entry means one page — `host` holds the page URL verbatim (`normalize` never appends the trailing "/" it adds to an immich base URL), any number of web entries is allowed, and duplicates of the same URL are dropped) — plus `selectedTimeZoneId`, `quietHours` (list of raw 5-field cron expressions, `minute hour day month weekday`; the screen is off whenever **any** expression matches the current minute in `selectedTimeZoneId`, overlaps simply OR), `interval` (minutes between assets; **default 5** per `Configuration.java:44`, and read as `Math.max(1, …)` everywhere, so 0 or a negative value means "as fast as it can go" rather than off), and `autoReboot` (the kiosk watchdog's permission to reboot the device as its last rung; absent/false means it never reboots, and the rungs before it — re-rotate, redraw, repair Wi-Fi, restart the app — are unaffected by the flag; editable in the options dialog and in the trusted-network-gated web config editor). The flat `host`/`userid`/`password` fields are `@Deprecated` legacy: on load, `Configuration.normalize` migrates a legacy flat config into a single immich backend (and re-saves it); on save, `SettingsManager` mirrors the first immich backend back into the flat fields so older APKs can still read the file. The `@Deprecated` `startQuietHour`/`endQuietHour` pair is legacy in the same way: on load it migrates into a single cron expression in `quietHours` (parser: `CronExpression`), and on save a single mirrorable whole-hour window is written back — anything richer degrades to -1/-1 (off, never wrong hours). The **trusted-network** flag is intentionally *not* in `configuration.json`: it lives in the app's default SharedPreferences (key `trusted_network`, off by default, toggled by the *Trusted Network* checkbox in the options dialog) and gates the LAN web server's config endpoints (`/config`, `/config/download`, `/config/import`), which additionally require the per-device **configuration token** as the `token` query parameter (32-hex, lazily generated with `SecureRandom`, persisted under `trusted_network_token`, shown only in the options dialog while the flag is on) — and the two write endpoints enforce a same-origin `Origin`/`Referer` check (see [docs/WEBSERVER.md](docs/WEBSERVER.md)). The **device name** follows the same rule (key `device_name`): it labels one box, so it is kept in SharedPreferences, never serialized into the configuration document, and therefore cannot travel through `/config/download` or `/config/import` and relabel another frame. It is set in the options dialog's **About** tab (which commits on its own button, not on the dialog's Save, because ViewPager2 destroys an off-screen page's views) or by `POST /devicename`; both go through `SettingsManager.setDeviceName`, the only sanitiser, and neither restarts the rotation. Empty means unnamed, and every surface then identifies the frame by platform and IP address alone, exactly as before the field existed. The **backlight level** follows the same rule (key `min_brightness_step`, the opaque step index `BrightnessManager` interprets): it is per-device hardware state, so it is kept in SharedPreferences, never in `configuration.json`, and never exported — importing someone else's config must not silently change how bright this frame is. It is written with `commit()`, not `apply()`, because the frame is routinely power-cycled or crash-exited a moment after the tap and a level that never reached disk comes back as the 0.3 floor on the next boot. Who may change it: on an EO1 the BACK button, and on either frame the web page's `brightness` action (POST-only, because it is the one action whose effect outlives the request) — the step-and-persist path is deliberately not capability-gated, because the EO2 has no button and this value is its only brightness. The **read** is held to the same standard, because "this frame was never adjusted" and "the store would not say" both used to answer `0` — which is also the dimmest step, so one silent failure dimmed the panel and the next tap persisted the dimming as if it had been chosen. `SettingsManager.readMinimumBrightnessStep()` therefore distinguishes `STEP_ABSENT` (the floor is the honest answer) from `STEP_UNREADABLE` (the answer is the last level this process saw on disk — a process-static cache, since `MainActivity.onCreate` rebuilds `SettingsManager` and a re-creation is exactly the event being survived), and `BrightnessManager` records which it got as `stepSource`/`authoritative` in `/state`. A level that was guessed is never grown from: the first step after such a read re-reads the store and steps from what is on disk — but every press still advances the panel, authority cleared or not, because the button is how an operator recovers a dim frame and a store that answers neither way must not be able to freeze it; whether the change outlived the process is the separate `durable` fact. A step outside this build's range clamps to the **nearest end**, not to the floor. And the BACK button's wrap from the top step down to 0.3 stays as it is — it is how a frame comes back down without a second control — so what a "it dimmed by itself" report gets is a record of who moved it (`/state`'s `lastChange`, plus one line in `eo1-app.log`, which survives; logcat holds ~13 minutes), not a removed destination.

**MQTT** (options dialog tab **“Media”, “MQTT”, “About”** — `OptionsMqttFragment` / `options_mqtt.xml`): five fields in `Configuration.java` (`mqttHost`, `mqttPort` default 1883, `mqttProtocol`, `mqttUser`, `mqttPassword`; host and protocol are free text — the layout's own hints are `e.g. tcp://192.168.1.155` and “tcp, ssl, ws, etc.” — and `MainActivity` joins them into `protocol://host:port`), also editable in the trusted-network web config editor. What the feature does is narrow and easy to over-read, so state it exactly: `com.aphex3k.eo1.mqtt.MqttManager` builds a Paho client only when `mqttHost` is non-empty, **subscribes to one topic — `sonos/+` — and publishes nothing**, and with no broker named it is never constructed at all. A Sonos coordinator's `transportState` — `MqttManager.PLAY_STATES` (`PLAYING`, `GROUP_PLAYING`) and `STOP_STATES` (`STOPPED`, `PAUSED_PLAYBACK`, `GROUP_STOPPED`, `GROUP_PAUSED`) — drives `MainActivity`'s now-playing banner: title, artist and group name painted over whatever the rotation is currently showing, then faded when the track's own duration elapses. **No MQTT message rotates an asset, installs an update, or reconfigures anything** — there is no command vocabulary on that topic. a broker URI whose scheme begins `ssl` is given the same anchored `SSLSocketFactory` (`ApiServiceGenerator.trustAnchoredSocketFactory`) as the OkHttp clients, so a broker behind a current certificate is reachable from MQTT too (`docs/TRUST.md`); `mqttUser`/`mqttPassword` are credentials and therefore belong to the cleartext-in-`configuration.json` warning above.

### GitHub dependency reporting

`.github/workflows/dependency-submission.yml` (on push to `main` + manual) resolves the `:app` classpaths with Gradle (no tests, no packaging) and submits a dependency snapshot to the GitHub dependency graph (`POST /repos/…/dependency-graph/snapshots`). Local preview:

```bash
./gradlew :app:dependencySubmissionSnapshot   # writes app/build/dependency-submission-snapshot.json
```

The Gradle wrapper jar is deliberately a regular git object, not LFS: this repo is a GitHub fork and cannot serve its own LFS objects, so a plain checkout would leave the wrapper as an LFS pointer and `./gradlew` could not start in Actions. The blanket `*.jar` LFS rule in `.gitattributes` is overridden for it — keep it that way.

## Do / don’t

**Do**

- Keep API 19 compatibility and existing Retrofit/OkHttp pin strategy
- On a breaking Immich API change, add a new frozen `com.aphex3k.immichApi.vN` DTO package + `ImmichClientVN` + a registry band in `com.aphex3k.media.immich.ImmichClientRegistry` — never edit a frozen client package
- Treat `app/src/main/java/com/aphex3k/eo1/` as the app core and `com.aphex3k.media` as the backend layer (per-backend client wiring; `MediaManager` only orchestrates)
- Gate platform-specific hardware behavior (soft-touch buttons, light sensor, screen brightness, power button) on `HardwareCapabilities` flags — never add model-specific `if`s on `Build.MODEL`/`Build.DEVICE` elsewhere; unsupported features no-op. Gate the **input device**, not the **capability**: `supportsBrightnessButton()` says whether a frame has a key that asks for a brighter floor, `supportsScreenBrightness()` says whether its panel accepts a brightness value (true on both — the window attribute is not platform-specific). Gating a *feature* on the button flag is how the EO2's brightness floor became unreachable by anything, since that frame has no button and its floor is the only brightness it has
- Keep the LAN web server dependency-free and resource-cheap (hand-rolled `ServerSocket`, `Connection: close`); every web-server thread must be defensively wrapped — a stray exception must never reach the global `UncaughtExceptionHandler` (which calls `System.exit(2)`)
- Write crash-path stack traces by walking the cause chain **iteratively** (`CrashStore.printTrace`), never `Throwable.printStackTrace`: that recurses once per cause, so a deep chain raises `StackOverflowError` on the dying thread — where the stack is already the suspect — and the whole report is lost. Also note `PrintWriter` has no `Throwable` overload, so `pw.print(error)` compiles to `print(Object)` and writes `toString()` only
- Let `libTsPlayer-jni.so` loop a media file **natively** — create the TsPlayer once per asset and run no per-duration Java teardown loop; full `deletePlayer` + `createPlayer` only on asset handoff / `stop()` / `surfaceDestroyed` (see [docs/TSPLAYER.md](docs/TSPLAYER.md) “Looping (native)”)
- Keep every adbd command line built from fixed constants — the install path (`AdbdInstallClient`, staged public-copy path only), the `service.adb.tcp.port` / `ctl.restart` writes in `ensureTcpAdbd`, and the `DeviceRepair` ladder (`svc wifi disable`/`svc wifi enable`, `reboot`, and the `pm disable com.geniatech.upgrade` / `pm disable com.electricobjects.updater/.{CheckUpdateReceiver,BootCompletedReceiver}` lines it runs once from `MainActivity.onCreate`) alike; never interpolate user/config/network input
- In `VendorPollers`, read a poller's **package** setting first and its components only as an OR after it: `getCurrentEnabledStateLPr` consults nothing but the component sets, so every component of a package disabled at package level answers `DEFAULT`, and a components-only check would report a correctly silenced frame as armed and force-stop a system-uid package on every launch. An unreadable read is `UNVERIFIABLE` (fall through to writing), never `QUIET`
- Let the kiosk watchdog escalate only *down* its ladder (rotation → redraw → network repair → self-restart → opt-in reboot), one rung per wedge, with the device reboot kept behind the options-dialog permission — an unattended frame should self-heal, but not silently hard-reboot in a loop

**Don’t**

- Commit `configuration.json`, `ffmpeg/`, or bulk `EO2/` dumps
- Modify a frozen Immich client package (`com.aphex3k.immichApi`, `ImmichClientV3`) in place for a breaking API change — add the versioned package + registry band instead
- Grow the rotation pool beyond compact `MediaAsset` records; the ~800MB device cannot hold full API response objects for large libraries
- Enable GitHub’s managed “Automatic dependency submission” for this repo — the repo’s `dependency-submission.yml` workflow (user submission) is the dependency-reporting path, and user submissions take priority over managed runs
- Introduce Kotlin or raise `minSdk` / `maxSdk` without an explicit product decision
- Add ExoPlayer / Media3 for video playback (known Geniatech API 19 full-system hang)
- Loop TsPlayer video with a Java per-duration `deletePlayer`/`createPlayer` (full-recreate) loop — the `.so` already loops natively; a per-duration recreate clears the Amlogic plane → a black flash every pass and fights the native loop. Also rejected for looping: `start()`-alone at EOS (EBUSY on `amstream_vbuf`) and create-without-delete (wedges after ~12 gens). Full teardown only on asset handoff / `stop()` / surface destroy. Pulse TsPlayer `SurfaceView` GONE→VISIBLE / `setFormat` only for normal show/hide, never to fix loop stalls (see [docs/TSPLAYER.md](docs/TSPLAYER.md) “Looping (native)”)
- Add TLS/HTTPS or any new heavy dependency to the LAN web server; keep it unsecured plain-HTTP on 80→8080 for the trusted LAN only
- Automatically delete files from the local media backend (`filesDir/uploaded`): user uploads and their compatibility sidecar reports are removed **only** by explicit user action (the web UI's Delete button → `POST /files/<name>/delete`, or on disk). The app may write a sidecar report next to a failing upload but never deletes, renames, or rewrites the report or the media file
- Serve files via the web server from anywhere outside `filesDir/uploaded` — the exceptions are the two stores this app writes about itself: `filesDir/crashes` (`GET /crash/<name>`) and the diagnostics store `filesDir/reports` (`GET /report/<name>`), both name-guarded and holding only app-generated content. `/data/anr`, `/data/system/dropbox` and logcat are never served in place: `CrashSources` copies them into `filesDir/crashes` first. `configuration.json`, SharedPreferences and `filesDir/updates` are read by no crash or report route and served by none — which a `DiagnosticsReport` collector must keep true: the `/state` document it embeds is built to omit credentials, and no collector may read the config document or the preferences directly
- Keep exactly one global `UncaughtExceptionHandler`, installed by `Eo1Application.attachBaseContext` (not an Activity's `onCreate` — a throw during `MainActivity.onCreate` must still be recorded). Its body may not throw and may not chain to the framework handler: the +120 s relaunch alarm and `System.exit(2)` are the contract `KioskWatchdog` and `UpdateManager` depend on, so they belong in a `finally` that a failed report write still reaches
- Where the app spawns a subprocess (`CrashSources` → `logcat -d -b system`), use `ProcessBuilder`/`Runtime.exec` with an **array** argv, an absolute binary path, and a compile-time constant — never the single-string form, never a directory listing or any value interpolated. Bound it by elapsed time *and* byte count and `destroy()` it: `Process.waitFor(long, TimeUnit)` does not exist before API 26, and a bare `waitFor()` before draining stdout can hang the thread forever. **Read the exit status**: stderr is merged into the stream we drain, so a rejected command otherwise looks like a successful capture of nothing
- Treat README marketing or hardware setup prose as build requirements for code changes
- Edit or rely on `EO2/`, `ffmpeg/`, or `.electric-objects/` as product source
