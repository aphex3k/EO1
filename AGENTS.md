# AGENTS.md — EO1 / EO2 Immich frame APK

## Goal

Android home-screen replacement APK for Electric Objects **EO1** and **EO2** digital frames. It rotates photos and videos on an interval so display never depends on Electric Objects’ cloud; the assets come from files uploaded to the frame's own LAN web server (`{"type":"local"` backend), a self-hosted [Immich](https://immich.app/) server, or both.

- Package ID: `com.aphex3k.eo1`
- Product source: `app/` (Java Android module)
- Human ops guide: [README.md](README.md); install / hardware bootstrap: [docs/SETUP.md](docs/SETUP.md)
- Hardware notes: [EO1-specs.md](EO1-specs.md)
- TsPlayer / Amlogic video: [docs/TSPLAYER.md](docs/TSPLAYER.md)
- LAN web server (upload / control / diagnostics): [docs/WEBSERVER.md](docs/WEBSERVER.md)
- TLS trust and the 2013 CA store: [docs/TRUST.md](docs/TRUST.md)
- GitHub Pages front page: [docs/index.html](docs/index.html) — a card that states the premise and links to the markdown, never a copy of it

## Tech stack & hard constraints

- **Language:** Java only — no Kotlin
- **SDK:** `minSdk` / `targetSdk` / `maxSdk` = **19** (KitKat 4.4.2); `compileSdk` 34
- **Build:** Gradle + Android Gradle Plugin; all builds are local (the old Jenkins CI is gone — `publish-update.sh` at the repo root builds + signs release APKs via `local.properties` signing props). Every build also carries its own provenance: `BUILD_DATE` (the commit timestamp), `GIT_SHA` and `GIT_DIRTY` as `BuildConfig` fields, generated **lazily** through `androidComponents.onVariants` + `providers.provider` — never a configuration-time `new Date()`, which rewrites `BuildConfig.java` and recompiles the whole module on every Gradle invocation, `test` included (AGP 8.x has no lazy `buildConfigField` overload; the variant `buildConfigFields` map does). `com.aphex3k.eo1.BuildFacts` renders it in one place for the options dialog's read-only **About** tab, `/state`'s `app` block and the web page header — without it a release build says nothing about itself on screen, since the version overlay is `BuildConfig.DEBUG`-gated. `BuildFacts` reads the installed signing certificate the same API-19 way `UpdateManager.installedCert()` does (`PackageInfo.signatures`, never `signingInfo`, which is `NoSuchFieldError` on KitKat); `BuildFacts.RELEASE_CERT_SHA256` is the expected release fingerprint the verdict line compares against — public data from `keytool -list -v -keystore <release.jks>`, to be re-read whenever the keystore rotates, and left blank means "not checked", never "mismatch".
- **Crash diagnostics:** release is R8-minified (`minifyEnabled = true`, and `proguard-rules.pro` keeps `SourceFile,LineNumberTable`), so a release trace is unreadable without the build's `mapping.txt`. `publish-update.sh` therefore archives it as `mapping-<VERSION_CODE>.txt.gz` beside the APK, and every crash report carries its `versionCode` in both file name and header — `versionCode → mapping` is 1:1 because the script enforces strictly increasing codes. The mapping is an archive for humans: it is deliberately **not** referenced in `update-manifest.json`, so no frame ever downloads it. If you disable minification you must still publish (or the escape hatch `EO1_UPDATE_MAPPING_OPTIONAL=1` makes the missing mapping loud instead of silent). **A trace read through `debug.sh` is filtered, not complete:** its `logcat_grep` is a whitelist, and on physical hardware every line passes through `grep -E`, so a dump arrives missing its `java.lang.X: message` header and every non-`com.aphex3k.eo1` frame — leaving a tail of app frames that looks like a contradiction (the stack of a thread at a line the source provably cannot throw from). The filter now carries anchored trace shapes for that reason, but the lesson outlives the fix: before reasoning from a partial trace, take one unfiltered `adb logcat -d -v threadtime`, and remember that on these frames the durable record is `files/eo1-app.log`, not logcat's ~13 minutes.
- **Networking:** Retrofit + OkHttp + Gson; hand-rolled Immich client; self-update via `com.aphex3k.update` (plain-HTTP manifest + pure-Java JAR signature verification + headless install). Headless install: `installPackage` reflectively when the app holds `INSTALL_PACKAGES`, otherwise the device's own adbd on `127.0.0.1:5555` (`AdbdInstallClient` speaks the minimal adb wire protocol and runs `pm install`; sideloaded frames lack the signature-level `INSTALL_PACKAGES` permission). **That protocol is fourcc-tagged messages, and the header's checksum word is a byte sum, not a CRC32** — both measured against a live daemon, because nothing negotiates them: tags travel as ASCII (`CNXN` = `0x4e584e43`, not the `0x0100000N` of old `adb.h`), and a CRC32 in the checksum field is answered with a closed socket. Before this was found the client emitted the `%04x`+`host:version` framing that belongs to the *host's* `adb server` on 5037, so adbd never saw a request and every `install`/`exec` reported `UNREACHABLE` after its read timeout — meaning the adbd transport had never worked on any frame, while `probe()` (a bare TCP connect) kept reporting `adbdReachable: true`. **Do not assume the ROM configured that adbd:** the EO2 ROM listens on TCP 5555 with `ro.adb.secure` unset, the EO1 ROM does not listen at all (`ECONNREFUSED`). The app may start it — `AdbdInstallClient.ensureTcpAdbd(allowed)` writes `service.adb.tcp.port=5555` + `ctl.restart=adbd`, rate-limited to one restart per 10 min — but **one action at a time and only when the operator enabled both `Trusted Network` and `Allow loopback ADB for update installs`** (`SettingsManager.isLoopbackAdbEnabled()`, both SharedPreferences-backed and default off), because TCP adb has no loopback-only mode and is reachable **as root** from anywhere routable. `teardownTcpAdbd()` (`port=-1` + restart) closes it in a `finally` the moment that install ends, so the exposure window is one install, never a boot; a daemon the ROM owns is never touched, and a note in the state file lets the next launch close a window an install's success left open. **Never arm it to be ready**: a `DeviceRepair` rung the watchdog has actually reached may start it for the duration of that one rung and closes it in the same `finally`, but the launch-time vendor `pm disable` only probes — adbd is never left listening because the app booted. An automatic cycle never shows the install-intent confirmation UI: a frame with no working silent transport leaves the update `STAGED` with `needsHumanConfirmation` set and says so in `/logs` + `/state` + the web page; the dialog appears only when the operator presses *Install on the frame* (never armed with the relaunch alarm, which used to fire the app back over a pending dialog). **A stage is not the end of the story, and `checkDue` no longer treats it as one:** while a *host-sourced* build is staged the ordinary check interval still re-reads the manifest, and `UpdateManager.judgeStaged` decides whether those bytes are still what is published — a higher `versionCode`, or the same code with a different `sha256`, means the published build is fetched and put through the four verification gates and **only then** replaces the stage, so a failed re-download leaves a frame holding the installable build it had before (state back to `STAGED` with the failure in `lastError`, never `FAILED`, which would stop the retry that is the only thing keeping an unattended frame current). Making that true took two separate fixes, because a stage is protected by two things — what is on disk, and what the state file says about it. **(a) The swap has one order and no destructive failure path:** `publishStagedPair()` renames the private master **first**, commits the state that names it, and replaces the installer-readable public copy **last** — because `runInstall()` re-hashes `stagedPublic` against the state, so a master newer than the public file is self-healing while a public file newer than the master reads as corruption and gets deleted. What the fix changed is the failure path, not the order: every rung after the master rename used to call `deleteStagedFiles()`, and `rename(2)` over `stagedMaster` unlinks the previous build there, so a build that had cleared all four gates could still leave a frame with nothing staged and its install retry dead. Neither route deletes the pair on a failed rename now. (`failOrRestore` reads the master to decide whether it can restore, and `runInstall` distinguishes the two ways the staged pair can look wrong: a master that does not hash to the state is the only case that may delete anything, while a sound master with an unwritable destination goes back to `STAGED` as `public-copy-failed`.) `failOrRestore` reads the master to decide whether it can restore, and `runInstall` distinguishes the two ways the staged pair can look wrong: a master that does not hash to the state is the only case that deletes anything, while a sound master with an unwritable destination goes back to `STAGED` as `public-copy-failed` — deleting a valid APK because copying it failed would destroy the thing the retry exists to fix. **(b) The two identities are persisted separately:** `UpdateState.expected*`/`manifestSha256`/`stagedSource` describe the APK on disk and are not touched by a check, while `fetch*` names the build being fetched and is promoted into the stage's identity only when the swap commits (`commitFetchedStage`). Writing the incoming manifest straight into `expected*` — which is what the first version did — meant a process killed during the download left state naming bytes that exist nowhere, the real stage sitting on disk unowned, and for an uploaded stage it also erased the `stagedSource` marker that was protecting it, so the next automatic check treated operator bytes as a stage it could overwrite. `reconcileOnStartup` now recovers either reading (`recoverInterruptedStage`: whichever sha the master matches, restoring the old identity or promoting the fetched one), and it may only ever add a stage back, never delete one — `VERIFYING` is also what `POST /update` parks in mid-swap. `mayDiscardStage` applies the same source rule to the one branch that deletes for a reason other than corruption, so a manifest that has stopped advertising a build cannot clear an upload. Serialization is what keeps that promise now, and it replaced a mechanism that could not. **One thread mutates update state and the staged files** (`com.aphex3k.update.SerialWorker`, deliberately free of `android.*` so its ordering rules are testable in plain JVM — which also means the product path never uses a `HandlerThread`, and a JVM test must not start one): every entry point — a tick's check, a forced check, an install attempt from the rotation tick or from the web button, an `update-reset`, an uploaded APK, and an install's `packageInstalled`/`packageInstallFailed` result — posts one item, and items run in order, each to completion. Nothing is revoked and nothing is attributed, so the vocabulary eight review rounds of this file accumulated is gone: no `updateWorker` thread token, no static `processOwner`, no `retired` flag, no `stageGate` monitor with a documented gate-then-monitor order, no per-worker `WORKER_SEQ` temp names, no ownership test next to a mutation. `UpdateManager` is a **process singleton** (`acquire()` from `MainActivity.onCreate`, `detach(listener)` from `onDestroy`) because the thing being protected is per-process: it holds the application context, never an Activity, and its listener is a `WeakReference` replaced on every recreation. The only identity comparison left is `detach()`'s reference check on that log sink, whose worst failure is one missing line — which is the honest residue, not an ownership mechanism by another name. Items coalesce by kind, so a queue cannot grow across a day of ticks behind one long download, and a coalesced item's priority only ever rises: a tick can neither stack a hundred checks nor downgrade an operator's Install click. Consequences, each of which a future edit can break: **(a)** a task that has started is never interrupted mid-commit, so a reset or upload queued behind a download is served *after* whatever that download already committed — correct by ordering, and the reason no `rename(2)` needs a lock held across it; the intermediate files are two fixed names again (`eo1-update.apk.part` in each staging directory) because nothing else can be writing them, and they are swept once at construction, which is all the ordering rule the once-per-process flag ever needed. **(b)** serialisation buys nothing across processes, so `INSTALL_PENDING` stays walled for exactly that reason — the platform installer holds `stagedPublic` open from another uid for the length of its settle window, and a check or upload arriving while one is pending is refused by a state-and-clock test, never a thread test. The clock question has exactly one predicate, `settleWindowExpired`, because the two places that ask used to disagree: the rotation tick waited the window out and the Activity's `onResume` roll-back rolled back **on sight**, so a screen coming back two seconds into a `pm install` that can take minutes cleared the wall while the installer still held the file. Alongside it, an install observer is bound to the stamp **that `persistInstallPending()` wrote**, returned up through `armAndPersist()` — never to `snapshot.installFiredAtMs`, which is the previous attempt's value and normally zero, and a zero that matches every pending state is not an identifier. `packageInstalled` carries no identity, so this is the case where ordering cannot help and a value has to. **(c)** it buys nothing across a process death either: the dual `fetch*`/`expected*` identity, the master-then-state-then-public order inside `publishStagedPair()`, and `atomicReplace()`'s refusal to delete-then-retry are all crash-durability, and deleting a guard must never be read as licence to delete one of those. **(d)** one thread means one stall is shared, which is the real cost: a socket that accepts bytes at zero rate would park every later action — including the operator's reset, which cannot preempt a blocking read — behind the client's read timeout, so the update client bounds a read to one minute rather than ten and lets the interval's retry do the rest, and `/state`'s `command`/`commandAgeMs`/`queueDepth`/`workerRunning` are how a silent queue gets diagnosed. Two distinct stall shapes, and the difference matters when reading `workerRunning`: a thread that was created and then died is unrecoverable and invisible — the loop is written not to exit, so `false` with a non-empty `queueDepth` is that case — whereas a thread that was never *created* (an out-of-memory is not exotic on this hardware) is retried by every subsequent post, so it self-heals within one rotation interval because `installStaged` is posted on every tick — which is the distinction a reader of `workerRunning: false` needs, and `SerialWorkerTest.aFailedThreadStartIsRetriedByTheNextPost` is what keeps the second half true. **(e)** a task that throws must not leave a `CHECKING` behind, because `checkDue` would then refuse every later tick forever and the per-recreation `reconcileOnStartup()` that used to clean that up no longer exists — the drain loop's failure sink settles the state, so keep that sink if you keep anything. **(f)** `POST /update` still answers synchronously, so its half runs on the web thread: the uploaded file is renamed out of the `apk_tmp_*` directory (whose `finally` unlinks it the moment the call returns) into a queue-owned `eo1-upload-<that directory's own name>.apk` **before** anything blocks, and a handback that times out answers `staging-queued` rather than a rejection, because the bytes are already somewhere the task can still reach. **A timeout is a statement about the caller's socket, never about the work:** `SerialWorker.await` removes nothing, started or not, and the giving-up caller deletes nothing it handed over. An earlier revision dropped a not-yet-started upload item on timeout and then unlinked its APK, which is a browser losing patience cancelling an upload the frame was still going to stage — so if a future edit wants cancellation, it needs its own explicit call, not a deadline. Two details that are not decoration: the slot is named after the request's temp directory rather than a fresh `System.nanoTime()`, because `rename(2)` silently replaces and a collision would stage one operator's bytes under another's answer; and the wait is bounded near what staging actually costs (~22 s measured for 18 MB behind a full check) rather than generously, because it occupies one of `WebServer`'s **three** threads and three parked uploads would take `/state` and `update-reset` down with them — the two things you need when the queue is wedged. **(g)** a log line must never be able to decide an outcome: `notifyDebug` swallows everything and `detach()` installs a reference-to-nothing rather than null, because both sit after commits — the one after `publishStagedPair()` in particular would otherwise turn a successful stage into `cycle-crashed`/`FAILED`, skip the install the same cycle was about to make, and re-download the APK every interval thereafter. The same reasoning puts `persistAdbArmed(true)` immediately after the port opens rather than after the pending-state write: a TCP adb listening as root with nothing in the state file naming it is an exposure no successor will ever close, because that flag is the only thing that triggers the close. **(h)** a preemption flag is read once per download chunk and nowhere else: it exists to stop finishing a transfer nobody wants, not to make ordering safe, and correctness must not come to depend on it. A cycle that stands aside because of it ends through `standAside()` — back to `STAGED` with its own stage if the frame had one, otherwise `IDLE`, and never `FAILED`, because recording a change of mind as a wire failure would stop the install retry for a frame that did nothing wrong. **(i)** `debugInformationProvided` is the only write path into `AppLogger`, so when no Activity is attached `notifyDebug` writes the durable line itself — otherwise every update event in the window this manager now routinely outlives an Activity reaches logcat only, and logcat holds about thirteen minutes. **(j)** `MainActivity.onCreate` calls `settingsManager.loadConfiguration()` **before** `UpdateManager.acquire()`, in that order, on every launch. `acquire()` hands the new SettingsManager to a worker that survived the recreation, and `getConfiguration()` is a bare field with no lazy read — so attaching first lets an already-queued check see an empty `updateManifestUrl`, settle as `manifest-url-not-configured`, and stamp `lastCheckedMs` as if it had contacted the host, silently costing the frame an interval after each rotation. The singleton's `attach()` is not a no-op on recreation for the same reason: the manager outlives the Activity, its configuration source does not. **(k)** reading state across threads is still allowed and still needs the monitor, because transitions assign several fields in place: `stateJson()` copies the state under the lock and builds its document outside it, so `/state` is a snapshot that may name a transition a moment after it began, and no reader may hold a lock the worker can sit on across IO.
- **Immich server:** supported band is the **whole 3.x line** (`3.0.0` up to, but excluding, `4.0.0`) — endpoints verified byte-identical through **3.3.3**. The band lives in `com.aphex3k.media.immich.ImmichClientRegistry` (the V3 client); each backend entry may pin its `apiVersion` (default `"auto"` = best-effort probe of `GET /api/server/version`). Ceilings sit on major boundaries, not on the last release someone checked: Immich marks its own stability in the spec (`x-immich-state`/`x-immich-history`) and defers removal of deprecated fields to the next major, so a 3.x minor cannot break a client that matched an earlier 3.x. A server **newer** than every known band is served best effort by the newest client and raises a one-shot compatibility warning through `MediaBackend.compatibilityWarning()` (toast + `/logs`) instead of being refused; a server **older** than the first band is still refused, because there we know the client speaks the wrong API. On a real breaking change, add a new frozen `com.aphex3k.immichApi.vN` DTO package + `ImmichClientVN` + one registry band; never edit a frozen client package. To re-verify the band cheaply, diff `open-api/immich-openapi-specs.json` in `immich-app/immich` between release tags for the operations this app calls (`ImmichApiService`) and the schemas they reference. **Authentication:** the configured `userid`/`password` pair is sent to `POST /api/auth/login` and nowhere else; that call's `accessToken` (a JWT — Immich's own session cookie carries the identical string, so there is no cookie jar in this app) is held in `com.aphex3k.media.immich.ImmichSessionStore`, one entry per host+user, attached as `Authorization: Bearer` by `ImmichAuthInterceptor` and reused across pool rebuilds and restarts. Immich 3.x has **no refresh endpoint**, so renewal is re-login, driven by the token's own `exp` claim (`JwtExpiry`) or by a 401 — never by re-sending credentials per request. The store is process-wide on purpose: `rebuildPool` news a backend per entry, and a client-owned session would mean a login per tick whenever the pool is failing. A failed login cools down for 60s rather than retrying; the token is mirrored in default SharedPreferences under `immich_sessions` and served by no web route.
- **TLS:** EO1 needs TLS 1.2 and weaker ciphers — see `Tls12SocketFactory.java` and `ApiServiceGenerator.java`. **Trust anchors are a separate problem from protocol**: the ROM's CA store is from about 2013 (measured on a live EO2: 156 anchors, 63 past their own `notAfter`, and **zero** Let's Encrypt/ISRG), so an Immich host on a current certificate cannot be validated by the device at all — which is why `ApiServiceGenerator.enableTls12OnPreLollipop` used to call `sc.init(null, null, null)` and now installs `com.aphex3k.eo1.trust.MergedTrust`'s manager instead: the platform's anchors enumerated at runtime, merged with `RootBundle`'s shipped roots. Three rules follow. (1) **Merging may only add.** If platform enumeration yields nothing, or the merged set is smaller than the platform's, the manager is not installed and the frame trusts what it trusted before — a narrowed set breaks hosts that work today and reports itself as a certificate problem. The same applies to the cipher list: `MODERN_TLS`' suites are kept and the two ECDSA-CBC ones are appended (this platform has no AEAD, so an ECDSA chain needs them named); *replacing* the list deletes TLS 1.2 GCM for every newer platform this code runs on, which is what the Immich live-tests caught. (2) **Roots are one of four gates** — anchors, ECDSA-CBC suites, server cipher policy, device clock (the app does no time sync, and LE lifetimes are 90 days) — so a fix must be reported as *which* gate it opens, not as a failed one. `/state`'s `trust` block names three of them (anchor counts + `missingBundleAnchors`, `gates.anyEcdsa`/`anyAead`/`supported`, `nowMs`); the one it cannot see is the **server's own cipher policy** (gate 3 of [docs/TRUST.md](docs/TRUST.md)), read instead from the failure's text (`handshake_failure` at `SSL23_GET_SERVER_HELLO`, before any certificate is looked at). `TrustCensus.classifyFailure` is that taxonomy in code, and `TrustCensus.gateNote` is how a frame reports it: appended to a backend's last-fetch record (the `backends:` line of the state dump and of a `Capture now` report) and to an update's `lastError`, which `/state` serves in its `update` block. It returns the empty string for a failure that is not about trust, and that is the half of the contract a future edit must not lose — a timeout carrying a `[TLS gate: ...]` suffix is what sends an operator reinstalling roots against a dead radio. The note belongs on the report, not in remembered state: a later healthy connection must not have to know to clear it. (3) **An app-local decision does not reach the kiosk WebView**: Chromium-33 validates in its own engine and ignores any Java trust manager, so an `https://` page still depends on the ROM store. Roots are not chosen here: `./update-roots.sh` takes the whole `/usr/share/ca-certificates/mozilla` set out of the pinned Debian `ca-certificates` package named in `certs/roots/debian.json` — version and SHA-256 from the suite's own index, every file re-checked against the archive's `md5sums`, anything past its own `notAfter` pruned with a printed reason — and rewrites `certs/roots/*.pem` plus `certs/roots/MANIFEST.tsv`, whose diff **is** the review. So the trust set is Mozilla's, a root Debian removes is gone from frames at the next release (there is deliberately no keep-anyway list), and **distrust latency equals release cadence** — say it that way rather than as an oversight. Nothing fetches during a build: `publish-update.sh` regenerates into a temp directory and refuses the release if `RootBundle.java` no longer matches `certs/roots`, if the manifest's count disagrees, or if a shipped anchor has lapsed, with `EO1_UPDATE_ROOTS_OPTIONAL=1` the only opt-out (the same shape as the R8 mapping's). That separation is load-bearing, not tidiness: `BUILD_DATE` is the commit's committer timestamp, so roots that varied without a commit would let two APKs carrying different trust material report one `GIT_SHA`. `./gen-root-bundle.sh` is the lower half (PEMs → Java constants) and now checks the set as well as each file — a duplicate fingerprint or a file name whose sanitized Java identifier is already taken aborts the generation, because at 120 inputs two labels for one certificate is expected, not exotic, and until that check existed the later file silently overwrote the earlier constant while both `Entry` rows still named it. Emitted as generated compile-time constants rather than `assets/`/`res/raw`, because release builds set `shrinkResources = true` and an anchor a shrinker decides is unreferenced is the wrong thing to discover behind glass. Two host dependencies in that path are measured, not assumed, and both will be re-broken by a plausible-looking simplification: **do not ask an openssl whether a certificate is expired** — `openssl x509 -checkend 0` calls a live 2046-dated root expired under LibreSSL 3.3.6 and valid under OpenSSL 3.5.9 (1 of the current 120, and the two agree on the other 119, including two other 2046 roots), so `cert-expiry.sh` compares `-enddate` against the clock in shell and all three scripts source it; and **do not compare generated bundles byte-for-byte across machines**, because a DN's rendering depends on which openssl printed it (`organizationIdentifier=VATES-…` versus `2.5.4.97=#0C0F…`) — the gate compares store names and PEM bytes. Note also that BSD `diff` cannot open a `<(...)` fd and reports that as a difference, so a process-substituted comparison refuses every release on a Mac. The `subject_hash_old` constants are **reporting keys** for `TrustCensus`, not inputs to a root shell: `MergedTrust`'s javadoc once promised a `CertStoreProvisioner` that has never existed in git and nothing here writes to `/data/misc/keychain`, so growing the bundle grows no adbd command list; the switch is `trust_bundle` in default SharedPreferences, **on by default** (unlike `trusted_network`/`loopback_adb`, this grants no privilege — it trusts public roots that arrived inside an already-signature-verified APK). It has **no UI**: no options-dialog checkbox and no web route writes it (`SettingsManager.setTrustBundleEnabled` has no caller), so switching it off means editing `com.aphex3k.eo1_preferences.xml` from a root or `adb` shell — and `RootBundle` ships whatever the pin says (120 anchors from Debian sid `20260816+nmu1` as of 2026-10-27; a suite choice is a trust decision, not a freshness knob — stable carries 148 including one already expired and keeps the Entrust roots sid has dropped), whose count `/state` reports as `trust.bundleSize` alongside `missingBundleCount` and at most 12 `missingBundleAnchors` names, because against a 2013 ROM store an untruncated list is ~110 strings inside a diagnostics section budgeted at 128 KB. `MergedTrust.create()` is memoized on the `enabled` flag for the same reason a bigger bundle is not free: a frame whose pool is empty rebuilds its backends every tick, and each rebuild re-parsed the entire bundle on top of enumerating the platform's 156 anchors — and a pool that is empty because TLS will not validate is exactly the state this bundle ships to fix. **Flickr is a separate measured case and should not be reasoned about by analogy with Immich:** the ROM's 156 anchors hold **zero** Amazon and **zero** Starfield/GoDaddy ones (measured with the same grep that produced the 156 figure, validated by it finding the 3 DigiCert entries it should), so the cross-signed intermediate that would otherwise let a 2013 store pass an Amazon chain is *absent* rather than merely unused, and neither half of `MergedTrust` covered it — the answer was always an added anchor, and Amazon's now arrive the same way as everyone else's. Validating each Amazon root *alone* as the only anchor showed both `api.flickr.com` and `live.staticflickr.com` close at **Root CA 1** (HTTP 200 for 1, handshake failure for 2, 3 and 4) even though the two hosts name different intermediates. And **cipher and protocol were never Flickr's problem**: TLS 1.2 with a CBC-only suite negotiates fine against its hosts, which is the opposite of the Let's Encrypt/Immich case. What none of that settles is whether KitKat's verifier tolerates the RSASSA-PSS signature those handshakes report — that still surfaces as a certificate error, and only `TrustCensus` on a real frame answers it.
- **Flickr:** `com.aphex3k.media.flickr.FlickrMediaBackend` adds a `{"type":"flickr"` backend, configured by `apiKey` (a Flickr *application* key — 32 hex, free for non-commercial use, applied for at flickr.com/services/api/keys/) and `source` (a photostream or album URL, or a username). **It ignores `host`:** the REST endpoint is a constant in `FlickrClient`, so there is no base URL to mistype, and `Configuration.normalize` must not give a flickr entry the trailing slash it appends for immich. `userid`/`password`/`apiVersion` are unused and `normalize` blanks the version pin for every non-immich type. **No OAuth in this build:** every listing method used answers an unauthenticated call, and signing `oauth_timestamp` would turn the frame's unsynced clock (docs/TRUST.md gate 4) into an authentication dependency on a device that is routinely power-cycled. Three consequences a future edit must keep true. (1) **The asset id is `hex(server)-hex(photoId)-hex(secret)`**, and `resolveThumbnailFallback` reads *only* `MediaAsset.id` — the display-error path reaches it through `assetFromKey` with a record whose type, dimensions, file name and paths are all empty, so a rule consulting any other field would hand the pipeline two different artifacts under one `<id>_fb.jpg` name with no checksum to tell them apart. Both halves are hex-encoded because the cache-ownership pattern applies to the **whole** file name and Flickr ids are not guaranteed hex: one `g`–`z` character makes those bytes invisible to eviction *and* to deletion. Extras **field names** are not URL suffixes (`url_l`'s suffix is `b`, and there is no `url_h`/`url_k` in `getPublicPhotos`), so never synthesize a URL from a field name. (2) **The ladder is the fixed pair `_b` (1024px) then `_z` (640px)**, because sizes at/above H carry their own secret that no listing returns — so an originals-capable rung must put its tier *in the id*, not read it off metadata — and because Flickr restricts everything above 1024px to paying accounts (measured 2026-10-26: `HTTP 410` at `_h`/`_k`/`_o`, `200` with real JPEG bytes at `_b`). That restriction is a property of **the account being read**, not of this app's registration, which is the whole of issue #94's "Flickr now requires Pro": say it in `compatibilityWarning()`/`describeVersion()` rather than descending a ladder whose upper rungs do not exist. Flickr reports no byte size and no checksum, which is survivable only because an unsized remote source now reserves *what fits* rather than `MAX_ASSET_BYTES`. (3) **`markIncompatible` stays the interface default no-op**: a `410` describes a subscription, never a decodability verdict, and there is no `EO1_*` tag on Flickr to write. A wire failure propagates **with** its cause (so `TrustCensus.gateNote` still appends `[TLS gate: ...]`) while a non-2xx becomes a **cause-less** `MediaDownloadFailedException`, because a `null` from `resolveOriginal` is the one acquire outcome `showNextImageLocked` does not count — an all-null pool refetches every catalog and re-sweeps recursively, offline, forever. Its ToU obligations (idle retention window that **restarts on each display of a still-listed photo**, eviction of photos that left the public listing, and a removal request durable across restarts because a bare delete is re-downloaded by the next tick) live in `FlickrRetention` and change no other backend's behaviour; deletion always goes through `MediaManagerInterface.dropCachedAsset`, which matches a prefix on an id the caller surfaced — never a glob, because a Flickr id's alphabet is an Immich UUID's.
- **Video:** Prefer Amlogic **TsPlayer** (`TsVideoView` + `libTsPlayer-jni.so`) on Geniatech EO1/EO2 when the native library loads; **automatic fallback** to platform `MediaPlayer` via `com.dd.crop.TextureVideoView` — and routing to the fallback is forced for videos whose display-matrix rotation is non-identity, and for videos whose displayed aspect is **not the panel's own shape** within `MediaCompatibility.VIDEO_NATIVE_ASPECT_TOLERANCE_BP` (3%, sized so H.264's 1088-padding stays native — 0.74% off — while the nearest common ratio to 16:9, 16:10, is 10% away; any value in 2-5% picks the same clips, so it is a margin and not a measurement). The TsPlayer `.so` has no scale/rotation control, so it can only be right when there is nothing to correct; see docs/TSPLAYER.md "Scaling & orientation (routing)". "Opposite" was the old test and it is now merely the largest case of "differs": that predicate compared a clip's two sides against each other and never looked at the wall, so a square clip — which has no long axis — fell through to TsPlayer and reached the panel letterboxed, and the comparison doubled as an unannounced threshold at aspect 1.0 (1088x1080 flipped engines while 1080x1080 and 1080x1088 did not). The rule lives in `VideoRoutingRule.allowsTsPlayer`, a pure function with a JVM test, because `MainActivity.routingAllowsTsPlayer` sits inside an `Activity` behind a header probe and had none — a change that moved most of a frame's library from one engine to the other left the entire suite green. On an EO1 the whole clause is moot and provably so: `selectVideoPlayer` ANDs routing's answer with `preferTsPlayer`, which is false there, so "always MediaPlayer on an EO1" is structural rather than a routing outcome. A non-native clip is also not fetched as an original, because MediaPlayer compositing it runs below realtime, so the source gate routes it to the backend's lighter stream instead — at any size on a frame with two engines, and still only at 1080p on a one-engine frame, for the reason given below. It still reaches MediaPlayer, and still with a fill crop: routing changes the stream, not the composite. **TsPlayer is not available on an EO1, and never will be** — the EO1 and EO2 carry significantly different silicon and the Amlogic player belongs to the EO2's board — the EO1 is an NXP i.MX6Dual (`MCIMX6D5EYM10AC`, read off the die in `_img/eo1-processor-fullwidth.jpg`), the EO2 is Amlogic (`ro.hardware=amlogic` in its own prop dump); see [docs/RESEARCH.md](docs/RESEARCH.md) §1. State that in code on two axes, because a model string cannot answer a silicon question: `HardwareCapabilities.supportsTsPlayer()` is the **model** answer (false on `Eo1Capabilities`, true on `Eo2Capabilities` and `GenericCapabilities`), and `VideoSilicon.allowsTsPlayer()` lets confirmed Amlogic silicon permit the engine whatever name the frame answers to — real EO2 hardware reports `stvm8b` / "Quad-Core Enjoy TV Box" and matches no model string. **Silicon may only permit, never forbid**: the EO1's i.MX6 identification comes from a die photograph in `_img/` and a third-party teardown, not from that frame's properties, and inventing "known not-Amlogic" strings would fail closed on hardware nobody has measured. An unrecognised board therefore defers to its model profile, and keeps its engine. Consult the resolved answer **before** `TsPlayerNative` in `MainActivity`, in that order, and read the native answers once behind that test and store them: Java evaluates a method's arguments before calling it, so one `TsPlayerNative.isAvailable()` inside a log line or a `/state` field initializes the class, runs `System.loadLibrary`, and restores the very warning the ordering exists to prevent. No JVM test can distinguish "loaded and failed" from "never attempted", so that is held by structure, not by a test: one call site in the startup and diagnostics path (the rest live in `TsVideoView`, behind a controller a denied frame never selects), because a JVM host answers `false` whether the load failed or was never attempted. A diagnostic read added outside the gate is the regression to watch for, and nothing will fail when it happens. so a correctly-detected EO1 never attempts the `dlopen` and never logs a linker error: on that frame the `UnsatisfiedLinkError` is a non-explanation of a hardware fact. Because of that flag the factory must identify each board **positively**; it used to ask only "is it an EO2?" and hand everything else the EO1 profile, which was harmless while the two differed only in buttons and sensors. Unrecognised hardware therefore gets `GenericCapabilities` — an EO1's input profile with every engine left on, reported as `platform: "generic"` — because an EO2 whose `Build.MODEL` merely changed spelling would otherwise lose its preferred player for a string reason, silently. Real EO2 hardware exists that does not say "eo2": `stvm8b` / "Quad-Core Enjoy TV Box", from an EO2's own recovery log, and `HardwareCapabilitiesTest` pins it. Do not propose shipping `libsystemwriteservice.so`, loading it conditionally by absolute path, or patching the vendor blob: the whole branch is closed and `docs/TSPLAYER.md` ("TsPlayer on the EO1: closed") keeps the one reason worth remembering — `getSystemWriteService()` inside that blob polls for the `system_write` registrant with no counter and no timeout while holding a process-global mutex, reached from the main looper by `createPlayer`, so on a ROM that never registers it the one-line fix converts a working frame into a dead UI needing a cable. A registered-but-deaf service, by contrast, is harmless: the EO2's answers `readSysfs could not contact remote` ten times a second while its video paints, so sysfs is not load-bearing for playback. What being permanently single-engine costs an EO1 is the `ORIGINAL_REPLAY` rung — a frame with one engine has one attempt at the original, which is exactly why the display-path byte-identity guards and the render-silent-versus-tag distinction carry more weight there than on the EO2. `VideoEngineReport` is the single place that turns those inputs into one word, so a routing line reading `player=TsPlayer` on an EO1 was a false statement about the frame rather than the clip and is now not. Two engine lines mean two different things and neither is more correct: the durable `video engine:` line states the frame's **default** once per launch (written on every launch, not only on failure, because an engine that loaded otherwise leaves no record that survives a reboot), and the per-clip `displayVideo routing: … player=` line states the engine that will composite *that* file — so a healthy EO2 legitimately says `TsPlayer` at launch and `MediaPlayer` for a rotated clip. Do not tell a reader to prefer one line over the other. Per-clip `/state` fields must name the engine that is actually compositing: `generation`, `errors`, `playerCreated`, `surfaceReady`, `recreatingForLoop`, `path` and the whole `loopPerf` object were read off `tsVideoView` **unconditionally**, so for a MediaPlayer clip every one of them described a hidden view playing nothing — which became the common case rather than a corner once every non-native aspect routed there. They are now gated twice: first on whether a clip is on the panel at all (see the **Reporting** bullet), then on `videoPlayer == tsPlayerController` within that, and `loopPerf` carries an `engine` property. **The MediaPlayer path's two fields are `manualLoopRestarts`/`manualLoopCycleMs` and deliberately do not reuse TsPlayer's `loopCycleMs` name, because they are not the same measurement**: with `setLooping(true)` the platform player loops inside itself and raises no callback at all, so a clip looping perfectly reports `0`/`-1` here forever — that is the design, not a stall, and reading it as one will send an operator chasing a frame that is fine. These count only restarts this process issues (`onVideoEnd`, or the position watchdog's seam), which is still the useful signal: a rising count against a `manualLoopCycleMs` far below the clip's duration is the seam firing twice. Liveness on that engine is `painted` and `playbackRateX100`. `durationMs`/`positionMs` were said to be fixed this way, but the fix was for *engine*, not for *asset type*: with a photograph on the panel they went on calling a released player from the web server's thread while the UI thread was tearing it down. They are now **absent** unless a clip is on screen, which is the only answer that cannot be a lie. **Do not use ExoPlayer** (including 2.19.x / Media3) — it triggers MediaCodec/GPU driver lockups that hang the whole device (ADB dies; requires power-cycle). See [docs/TSPLAYER.md](docs/TSPLAYER.md).
- **Web pages ("kiosk web"):** `com.aphex3k.media.web.WebsiteBackend` puts a configured page URL into the rotation pool as a `MediaType.WEB` asset. It has no bytes: `MediaManager` never runs it through `acquireAsset`/cache/integrity, and hands the URL to `MainActivity.displayWebsite`, which renders it in a chrome-less platform `WebView` (no extra dependency, no `@JavascriptInterface` bridge). The view is created lazily on the first web asset and inserted above the image view — a frame with no web backend must never load a WebView provider, and every other display path must hide it again. Whether it *worked* is only known asynchronously, so failures bypass the `assetFallback`/`tagAssetAsIncompatible` path entirely: `onReceivedError` or a 30s load watchdog calls `MediaManager.webDisplayFailed`, which reveals the image underneath and advances to the next pool asset (capped per cycle). A ROM with no usable WebView provider must degrade to skipping web assets, never crash into `System.exit(2)`. The engine is Android 4.4's Chromium-33 WebView: expect LAN-hosted or deliberately legacy pages over `http://`, not modern SPAs.
- **No client-side transcoding / conversion:** The downloaded Immich original is used as-is — there is no on-device FFmpeg, video re-encode, or image resize. **Nothing in `fetchCatalog` filters on decodability, and no asset is judged by a file name that merely *could* hold a bad codec (`.mov`, `.mp4` are containers, not verdicts).** Every image and video the account can see joins the rotation pool (`ImmichMediaBackend.isDisplayable` checks media type and trash only), and each one is *displayed*: the original is always the first attempt, and a display failure moves one rung down a strict ladder — original → (video only, and only while `preferTsPlayer` is true) the same original on the other player engine → backend fallback (Immich `/thumbnail?size=preview` for stills, `/video/playback` for video) → flagged; a **local upload has no degraded source at all** (`MediaBackend.resolveThumbnailFallback` is the interface default returning null for `LocalMediaBackend`), so its ladder is one rung shorter and its last rung dead-ends. Only the last rung decides incompatibility, because metadata is the one thing that can be stale: an operator who regenerates thumbnails, or a server that upgrades its HEIF handling, gets the asset back into the rotation on the next pool rebuild with no app change and no tag to clear. Failing to *fetch* an original counts as that rung failing: `MediaManager` falls through to the degraded source instead of reporting the asset as an error, because the ladder — not the rotation loop — is what decides. The exception is a failure with a cause (an `IOException` from the wire): that is nobody's asset, it propagates, and a frame with no network must not spend a thousand thumbnail requests proving it. Five throughput/size/orientation gates route, and none of them ever drops or tags an asset: originals above `MAX_ASSET_BYTES` — **1 GiB** (`MediaManager.java:58`), a per-file ceiling and not a capacity claim: the ~800 MB figure elsewhere in this file is *total* app storage on this hardware, so what binds one download is the smaller of 1 GiB and the free space left after `MediaCacheManager.SAFETY_MARGIN_BYTES` (128 MB) —, videos with a coded side over 1920px (`MediaCompatibility.incompatibleVideoResolution`), and videos whose sustained macroblock throughput exceeds `MediaCompatibility.MAX_VIDEO_MACROBLOCKS_PER_SECOND` (`incompatibleVideoThroughput`, from coded size x frame rate), and videos whose sustained video-track bitrate exceeds `MediaCompatibility.MAX_VIDEO_BIT_RATE_BPS` — **15 Mbit/s, decimal** (`incompatibleVideoBitrate`, from the `moov` `stsz` byte total over the track's `mdhd` duration; the average, since the probe measures no windowed peak, and the operator's 14.4-smooth / 15.6-choppy datapoint is itself an average bitrate), and video whose **displayed** aspect is not the panel's own shape (`MediaCompatibility.incompatibleVideoUpscale`, from the `stsd` size, the `tkhd` display matrix and the frame's measured `MediaCompatibility.PanelShape`). Its mechanism is weaker than its siblings' and must not be over-claimed: `cropScaleFactors` depends on the clip's **aspect** and the viewport alone — `(1080,1920,1920,1080)` and `(1080,1920,1280,720)` both come out at `(3.16, 1.0)` — so routing to a smaller transcode leaves the composited region identical and buys only fewer decoded and sampled source pixels, and by that same arithmetic a 720p mismatch costs the same composite while a 1920x800 letterbox costs more — which is why the gate is no longer scoped to 1080p on a frame that owns a second engine: the viewport bounds the crop, so the clip's own size was never what put it over the margin. On a one-engine frame (an EO1, or any board whose `.so` never loaded) the 1080p size pair still limits it, deliberately: what such a frame downloads must not move because of a change to an engine choice it cannot make. The honest cost of that scoping is that an EO1 goes on compositing non-native originals below realtime, exactly as before. Both halves ask the same `videoAspectDiffersFromPanel`, so "native" keeps one meaning; only whether the size pair still bounds the gate depends on the engine count, and `VideoRoutingTest` plus `cropGateKeepsItsOriginalScopeOnAFrameWithOneEngine` pin both halves. The datapoint `cropScaleFactors` itself records is a different case again (a double axis-swap applied to an already-aligned clip), so if a routed clip still runs slow the lever is fill-versus-letterbox in `TextureVideoView`, not the source, and the predicate now names the fill factor itself in its reason string — pinned by asserting that the number equals what `TextureVideoView.aspectScale` computes for the same clip-and-panel pair, so a report cannot drift from the compositor it describes. The predicate is the aspect clause of the routing rule below, not its rotation clause: a clip the matrix has already turned to match the panel needs no crop beyond 1:1 and must pass. **All five choose a source, and therefore apply to remote backends only:** `MediaManager.originalUsable` returns true the moment `asset.localPath` is set (`MediaManager.java:952-990`), so an uploaded file is never **source**-routed around its own size, coded dimensions, frame rate, bitrate or aspect — it is displayed at whatever it arrived as, in slow motion if the decoder cannot keep up. "Never source-routed" is not "never routed": an upload is still engine-routed, so a square upload on an EO2 now goes to MediaPlayer rather than being letterboxed by TsPlayer — and it has no degraded rung behind it. That is deliberate, not an oversight: a local upload has no degraded source to be routed *to*, so gating it would mean not showing it at all. The first two are decided from catalog metadata before any download. The third, fourth and fifth cannot be: no backend reports a frame rate, a bitrate, or a display matrix, so all three are judged from the `moov` of the original once it is on disk (`VideoHeaderProbe.StreamStats.fpsMilli` / `.bitRateBps`, and `Probe.rotationDeg`), which means the asset's first appearance pays one original fetch and then descends to the fallback inside that same acquisition — and every later acquisition of it starts at the fallback, because the verdict is remembered per asset key for the life of the process. The bitrate gate fires on strictly fewer files than the throughput one, because a truncated `stsz` leaves the byte totals unknown (`bitRateBps` -1) while still yielding an `fpsMilli` — the correct conservative direction, but it is coverage, not certainty. The orientation gate has a third unknown of its own, and it is the reason `MediaManager` carries the panel's orientation as a value rather than reading it: `MediaManager` has no `Context`, so `MainActivity` publishes the panel's measured `PanelShape` through `publishPanel`. **The refresh mechanism is a layout-change listener on the root, and nothing else can be**: `onConfigurationChanged` runs *before* the view tree is re-measured, so reading bounds there can hand back the pre-rotation size, and a panel turned by the ROM post-processor need not produce another focus callback at all. Republishing on each real size change is also the only path that survives `displayVideo`'s same-path early return — without it a pool holding one video keeps the shape it measured before the frame was moved, and both the source gate and `/state` go on deciding against a wall that is no longer there. `onCreate`, `onConfigurationChanged` and `onWindowFocusChanged` also call it so a value exists before the first asset, and `displayVideo` calls it again on the UI thread so engine and source decisions cannot be judging two different panels; both are convenience, not the freshness guarantee. A shape replaced a `Configuration.orientation` boolean because an orientation flag cannot tell a 16:9 panel from a 16:10 one, which is exactly the question the rule now asks; `frameOrientation` survives as the *same* number rendered as a word, derived rather than separately measured, so the two cannot disagree. Read it from the **root view**, never a video view: `onCreate` sets the idle engine's view to `GONE` and a `GONE` view is never measured, so a video view would report 0 forever on precisely the frames this rule exists for. `/state` carries `video.panelShape`, and `panelShape: "unmeasured"` is the single field that distinguishes "the rule is working" from "the rule is dark and every clip kept TsPlayer" — the latter looks identical to no regression. An unpublished panel keeps the gate dark, which is the conservative direction: a frame that cannot say how it is hung shows its originals. It also gets its own verdict map, `upscaledVideoKeys`, in which every entry carries the panel shape it was decided under and is honored by `originalUsable` only while that is still the published value — clearing the set on a change is not sufficient by itself, because the rotation and prefetch threads read the shape and write the verdict as two steps, so a clear racing between them would leave a verdict that outlived the panel which produced it and quietly retire part of a correctly-hung library on a frame that had merely been moved. A byte budget needs neither: it is a property of the file, and holds however the frame is hung. All five exist for the same reason: that decoder fails *without raising an error*, so waiting for a failure would show garbage or slow motion forever and never reach the fallback. Throughput, bitrate and orientation in particular must never reach `tagAssetAsIncompatible`/`knownIncompatibleKeys` — the clip is decodable, merely beyond the hardware or beyond the panel it happens to be hung opposite, and a verdict that could not be undone by a later server-side transcode would be a lie about the user's library. If that transcode is later produced, the gate notices on its own, because the fallback is not fetched blindly: `ImmichMediaBackend.resolveThumbnailFallback` first asks the playback URL how big its answer would be (`Range: bytes=0-0`, total read from `Content-Range` on a 206 or `Content-Length` if the server ignored the range) and carries it as `MediaSource.expectedBytes`. When that is **not smaller than** the asset's own `sizeBytes` the server has nothing worth degrading to: equality means the "degraded source" is a second copy of bytes already held — which cost a real 158 MB asset being fetched and cached twice at 0.18x — so `MediaManager` takes the original instead and records the asset as having no transcode (a "smaller" transcode that is merely *bigger* is refused by the same comparison — equality alone was enough while this gate only fired at 1080p, and went silently negative just below a server's transcode ladder, which is exactly where the widened crop gate reaches), a mark that also stops the throughput verdict and the probe from re-triggering each other every cycle. A probe that cannot answer is read as "worth fetching", the direction that can never skip a fallback that would have worked — and because that is a heuristic rather than a proof, `acquireFallbackSource` compares the finished artifact's length against the asset's and deletes it when they match. A byte-identical fallback must never exist on the device, not merely be unlikely: it is double the bytes, and it competes with useful files for eviction on a device with about a gigabyte free. Deletion therefore covers both directions — one written now, and one left behind by an older build. It has to hold on the **display** path too, which is the harder half: that rung has no pool record to consult, only what `assetFromKey` can rebuild from an opaque key, and that record's `sizeBytes` is always null — so every byte-identity guard is structurally dark there unless `fallbackAssetFor` first borrows the size and names from the asset still in hand. Borrow everything *except* `type`, which stays the caller's: `isVideo` is what selects `/thumbnail?size=preview` over `/video/playback` and what gives the artifact its `_fb.jpg` name, and `showRenderSilentStill` passes false for a video on purpose — letting a VIDEO record through there makes a silent clip re-fetch and re-decode the exact stream that produced no pixels, under a name eviction and deletion no longer recognise. Three rules come with that skip, and each is load-bearing only there. When the rung runs out because there is nothing distinct to fetch, what the dead end *means* depends on the rung above it: `MainActivity` passes `silentDescent` down from the paint watchdog alone, and the dead end then records render-silence and shows the still preview instead of tagging — the skipped download used to be the observation that produced that verdict, so a frame that declines the fetch must not write `EO1_INCOMPATIBLE` for a clip this device merely cannot draw, while a descent that followed an explicit refusal still tags. The post-acquisition length check has to exist on this path too, because `acquireRemoteFile` reuses a cached file against no size at all: a duplicate the probe could not prevent is still a duplicate once it is on disk. And the remembered no-transcode mark stands in for a probe that could not answer and never overrides one that did, so a transcode the operator generates later is used on the next failure rather than after a power-cycle. The original is kept cached rather than discarded as the other verdicts do. Their fallback artifact is cached exactly like an original — same integrity gate, same `<name>.sha1` sidecar, under a distinct `<uuid>_fb.<ext>` cache name so it can never evict-match the original it stands in for. A leading-`ftyp` byte check still runs on downloaded originals (catches HEIF content named `.jpg`), and so does a video sample-description check through `VideoHeaderProbe` — the one place a `.mov`'s real codec is readable, since the container extension is a claim rather than a fact (catches HEVC/AV1/Dolby-Vision content named `.mov`, the everyday iPhone case). It runs on the degraded artifact too: a server with nothing transcoded answers `/video/playback` with the original bytes, and that last rung is now flagged instead of painted black. An asset whose bytes are verified undecodable is remembered for the life of the process so its original is not re-downloaded every rotation, and retried after a restart. Flagging writes the Immich `EO1_INCOMPATIBLE` tag through `MediaBackend.markIncompatible`, which runs on the manager's tagging thread and lets every failure propagate (`ImmichApiTagException` carries the server's status line); `MediaManager` reports it to `/logs` and `eo1-app.log`, never to logcat alone — a tag the server refused must not be indistinguishable from an asset that never needed one. That tag is **operator-facing only**: the app never reads it back as a filter, and re-tags an already-tagged asset on every double failure, so a fixed asset needs no app-side unfreezing and a stale tag cannot retire one. For local uploads, the failure the **scan-time** check sees is made durable — and only that one: `LocalMediaBackend.fetchCatalog` writes a plaintext sidecar report `<name>.incompat.txt` next to the file on first failure (`com.aphex3k.media.local.CompatibilitySidecar` — exact reason, user-actionable fix, JSON diagnostic block); while that sidecar exists the asset is excluded from the rotation pool, sidecars are never part of the rotation themselves (`.txt` is not a media extension), and both the asset and its report are listed/served/deletable through the web server's `/files/<name>` — the only sanctioned way to re-admit an asset is to delete its sidecar. **A failure at display time is a different event and records nothing durable for a local file**: `markIncompatible` is the interface default no-op that `LocalMediaBackend` never overrides, and the display path writes no sidecar (`writeIfAbsent` is called only from `fetchCatalog`), so the next cycle attempts the same bytes again. The dead end is barely even visible: `displayFallbackSource` logs "backend 'local' has no fallback" to **logcat only** — no `postDebugInformation`, so nothing reaches `/logs` or `eo1-app.log` (which is exactly why the difference matters at 3 a.m., when logcat holds ~13 minutes) — and `tagAssetAsIncompatible` then succeeds vacuously. The one in-process exception is `renderSilentVideoKeys`, which a restart forgets. Do not describe a display-time upload failure as reported, tagged or retired.
- **Reporting describes the panel, not the last writer:** the recurring complaint — `/state` and the on-screen debug board describing the last video while a photograph was up, and the reverse — was never one field forgetting to clear. It was a missing question: nothing in either surface could ask *is a clip on screen right now*, so `video.active` answered "which engine" and every clip-scoped field was emitted unconditionally. The answers are `com.aphex3k.eo1.PanelDisplay` (a value type), `MainActivity`'s two writers `setPanelAttempt`/`panelNowProven` (what a display is putting up, and what is proven to be up), and `DebugBoard.visible` (which rows the panel entitles). Four rules follow, and each is a thing a future edit can silently undo. **(a) `PanelDisplay` is the only statement of what the panel holds**, and it makes the bug unstatable rather than discouraged: a `ClipFacts` reference exists **if and only if** its `MediaType` is `VIDEO`, enforced in the constructor, so reporting a codec or frame rate over an image requires reading a field that cannot exist in that state. `routingAllowsTsPlayer` therefore *returns* a `VideoRoutingDecision` instead of writing six fields — `lastVideoRotation`/`Width`/`Height`/`Codec`/`lastVideoStats`/`lastVideoDurationMs` are gone, and the two functional readers of that cluster (the loop seam's file duration, `setDisplayRotation`) read the record the attempt adopted. Do not reintroduce a stored per-clip field of any kind: the previous fix in this file's history cleared `activeVideoPath`/`activeVideoStage` at each handoff and left the rest alone, which is why the class came back. Reach both writers from seams rather than from a list of paths, because a list is what an earlier revision of this bullet had and it was wrong twice over: three paths were missing from it (`redrawCurrentAsset`, the `!ensureWebView()` return, and every image dead-end in `assetFallback` — the last of those after `removeFromCache` had already unlinked the file the record pointed at), and every path on it was calling at the wrong *moment*, because a display call is a decision and the panel changes later. The seams are: **`setPanelAttempt` from each display method** (`displayPicture`, `displayWebsite`, the render-silent branch of `displayVideo`, `startVideoOnController`), **`panelNowProven` from `noteDisplayProven()`**, which is already this file's own definition of "content proven on the panel" and is called at exactly the four handoffs that matter — and **`revealPhotoView(assetKey)`**, which uncovers the photo plane and proves it in one step, being the only way any recovery path reveals a surface whose bitmap is already loaded. A new recovery path that hides a surface by hand instead of calling `revealPhotoView` is the regression to watch for, and nothing will fail when it happens. `PanelDisplay.nothing(...)` is for the one case that is not a handoff *to* something: the operator asked the frame to forget the asset that was up (`stepAwayFrom`) and there is no other asset to show, so the panel must not go on naming a file it deleted — and it must not be written as an `image` with an empty path, which would claim a photograph on a blank wall. `videoPlayer` is now `volatile` for the same reason `activeVideoPath` was: `/state` reads it off one of `WebServer`'s three worker threads. **(b) Frame facts stay outside the record on purpose.** `panelShape` and `frameOrientation` are published by the layout listener whether or not a clip has ever played, and AGENTS.md's own requirement that `panelShape: "unmeasured"` distinguish a working aspect rule from a dark one only holds if that field is emitted while an image is up; so is `tsGate`, and `paintSignal` (a property of the controller class, not of playback). Everything else in the `video` block is a measurement of a clip and is emitted only for one — `VideoStateJson.build` returns early otherwise, which is a whole branch and not the six `if`s it replaced. `VideoStateJson` exists as a class for the same reason `VideoRoutingRule` does: while the block was lines in an `Activity` behind a live player, no test could ask what it says about a clip while a photograph is displayed, and the suite stayed green through two versions of that bug. The test supplies a probe that **throws** on any player read, so "the report consulted a released player" fails loudly rather than quietly returning `-1`. **(c) There are two panel records, because a display call and a visible change are different instants.** `attempt` is what a display path is putting on the panel; `panel` is what is **provably** on it, and only `panelNowProven` assigns `panel`. `panelNowProven` is called from `noteDisplayProven()` — each path's proof point, and nowhere else — plus the recovery paths that uncover a surface whose content is already loaded (`revealPhotoView`, a cleared panel). Those proof points are `Glide`'s `onResourceReady` (which is also where the browser view is hidden and the ImageView made visible), the browser's first proven page, and `revealVideoSurface` — which runs at *prepared* on TsPlayer, where no per-frame proof exists and the photo is stepped aside up front by design, and at the first composited frame on the platform player. **Each proof callback promotes the record it was created for** — `noteDisplayProven(mine)` from the Glide listeners, `noteDisplayProven(webLoadRecord)` from the reused `WebViewClient`, `noteDisplayProven(videoCompositing)` from the paint watchdog — because promoting "whatever attempt is current" lets a page that finishes loading during a photo fetch adopt the photo on the strength of a callback about something else; the wall is then described by whichever proof landed last, which is what it is. Two ownership fields make the live reads safe: `webLoadRecord` (which load a browser callback belongs to) and `videoCompositing` (**which record the player was handed**), both re-pointed at the adopted record on promotion and nulled when another surface takes the panel. `videoCompositing` is not redundant with `panel`: on a video→video change the outgoing clip is still the panel while the controller already plays the incoming file, so `probe.stale()` must test both or `/state` pairs one clip's path with another attempt's position, paint evidence and counters. Adoption also re-stamps the generation (`withGeneration`), because two paths can prove in the opposite order to the one they started in and `media.screen.generation` is only worth watching if it moves forward. Likewise `revealPhotoView()` takes the panel's identity from `provenPhoto` — the photo that last *loaded* — and never from its caller: the asset in hand during a recovery is the one that just failed, while the bitmap being uncovered belongs to something else, and an image view with no drawable must report an empty panel rather than an unnamed photograph. Stamping at the decision instead would have `MediaPlayer` report `onScreen: true` with a clip's measurements while the photograph was still covering it, would claim a photograph during a web→image transition while the page was still up (and for the whole interval if both image rungs failed), and — worst for the diagnostics story — would advance `media.screen.generation` on a wall that had not changed. `/state` therefore carries `media.current` (what rotation **selected**), `media.attempt` (what is being put up, present only while it differs) and `media.screen` (what is **up**); three moments, and the pairs of them answer different questions — `current` advancing while `screen.generation` does not is a frame that stopped painting, and `attempt` differing from `screen` for a whole interval is a display that is failing to land. The ladder's own reads follow the same split: the loop seam's file duration comes from `attempt` (a clip may be watched before it ever reaches the panel), while the player telemetry in `/state` and in the diagnostics report is suppressed unless the live controller still belongs to the snapshot being reported — `VideoStateJson` asks `probe.stale()` and drops `durationMs`/`positionMs`/`painted`/`loopPerf` rather than pairing one clip's path with another player's position. **(d) The debug board's lifetime is attribution, not eviction.** `debugInformation` used to have no `remove()` or `clear()` anywhere: ~58 writers each put a key forever, so the board printed the dead clip's lines beside the live photograph's, on the panel, in the common case. The first fix swept the map at each handoff, and that was the wrong mechanism twice: a sweep is an *ordering* rule, and these writes do not cooperate with ordering — `videoBudget`/`Show`/`Thumbnail`/`Incompatible` are posted from the media pipeline about an asset that is displayed a moment **later** (so the handoff deletes the verdict at the instant its subject reaches the wall), while `tagAssetAsIncompatible`'s failure line arrives from its own thread when a backend finally answers, which can be rotations **after** the asset left and which no display path can be made to precede. So each row now carries the asset it is about — `DebugInformation(key, value, assetKey)`, and `postDebugInformation` gained the subject for the nine media-pipeline writers — and `DebugBoard.visible(rows, panel)` renders frame rows (subject `null`, resolved from `FRAME_SCOPED` when a writer did not say) plus rows whose subject is what the panel holds. Nothing is destroyed, so nothing can be destroyed too early or too late; the map's keys are the fixed writer names, so it cannot grow and needs no reclamation at all. Two rows are **derived** rather than stored — `on screen` and `videoRouting`, both rendered from the record — which is what retires a clip's routing measurement when the panel stops showing video: an image record for the *same* asset (a failed clip covered by its own still, or an engine handover) carries no routing line, so there is nothing to print. **Two exceptions, both load-bearing.** `videoRouting` is rendered as `routingFacts + " -> " + engine`, never stored with the compositor baked into the sentence — a clip routed to TsPlayer and then handed to the platform player carries its original measurements, and a stored `-> TsPlayer` contradicted the `engine` field printed beside it. And `displayFailure` is the one asset-naming row that is **frame-scoped**, with the asset named inside the text: a failure explanation is needed precisely *after* recovery has uncovered another asset's photograph, at which point a row attributed to the failed clip is filtered out as not-about-the-panel, so every recovery would swallow its own diagnosis — while leaving it unattributed and undeleted would print a stale failure forever, which is the original bug. Naming the subject inside a frame-scoped row is the only combination that avoids both. `renderDebugBoard()` is called on a write *and* on a promotion, because printability depends on the panel as much as on the rows. The durable log is untouched by all of this and never filtered — `files/eo1-app.log` is a transcript of events rather than a claim about the present, and its write path (`Log.i` + `AppLogger` in `debugInformationProvided`) is the one thing no reporting change may touch; a verdict the board hides has to be readable somewhere. Board mutation stays on the UI thread under the existing `synchronized (debugInformation)` monitor that `/state`'s `debug` block also takes.
- **Video health is judged by pixels, not only by callbacks:** every other failure signal in the display path is a callback (`onError`, a throw in `onVideoPrepared`) or a *position* stall, and this decoder's documented failure mode is silent — bytes are accepted, `prepare` succeeds, the timeline advances, and nothing reaches the screen. So the MediaPlayer path supplies a real signal: `com.dd.crop.TextureVideoView.onSurfaceTextureUpdated` stamps the last composited frame (`VideoPlayerController.getLastFrameAtMs()`, `supportsPaintSignal()`; TsPlayer returns "no signal" because its `.so` offers nothing per-frame and its reported position is wall-clock when the native clock is unusable, so watching it would measure a timer). Three rules follow. (1) **A display attempt is armed with a paint deadline before any callback** (`MainActivity.startVideoPaintWatchdog`, `VIDEO_PAINT_TIMEOUT_MS`, mirroring the web path's `startWebLoadWatchdog`) so an attempt whose `prepareAsync()` never returns is still watched — the position watchdog cannot cover that case because it is armed *from* `onVideoPrepared`. While the panel is not ours to paint (quiet hours, `onPause`, the screen toggle) that poll **parks** instead of cancelling or spending its deadline, and `onResume`/`turnScreenOn` re-arm it with the parked time deducted and the video surface made visible again: a `TextureView` that is INVISIBLE composites nothing, so an unparked clock would sentence a healthy clip for the whole process on the strength of the app's own visibility bookkeeping. (2) **The photo is stepped aside only once a frame is proven to exist** (`revealVideoSurface`), never at prepare, and the ImageView is hidden rather than `Glide.clear`'d — clearing empties the drawable, and every recovery path reveals the photo by setting it VISIBLE, so clearing turned "restore the image underneath" into revealing an empty view over a black root. On an engine with no paint signal the hide stays at prepare. (3) **A confirmed no-pixels verdict skips and never tags**: a clip that reached the last rung and still rendered nothing goes into `MediaManager.renderSilentVideoKeys` (in-memory, per-process, forgotten on restart) and is shown as its `/thumbnail?size=preview` still instead of as a video, from `displayVideo`'s entry check onward — so later cycles never decode or display it, though acquisition still resolves its original normally (the skip lives on the display side, with the rest of the ladder). That verdict is deliberately **not** written to Immich: the fourcc tier states something about the file, this states only what this device's decoder did with it, and a wrongly-written `EO1_INCOMPATIBLE` outlives the frame that made it. The refusal is enforced inside `MediaManager.tagAssetAsIncompatible` (an asset in `renderSilentVideoKeys` is never tagged) rather than at the call site, because the substituted still re-enters the ladder's terminal rung — a preview the device cannot decode would otherwise reach the server through the one door the policy left open. The `ORIGINAL_REPLAY` rung is gated on `VideoRoutingRule.offersSecondEngineAttempt`, which needs three things where it used to check one: the frame owns two engines (`preferTsPlayer`), **routing actually chose TsPlayer for these bytes**, and that engine has fewer than `MainActivity.MAX_ENGINE_ATTEMPTS` attempts on them. The middle term is the fix — `displayVideo` re-derives the engine from the file's own header on every entry, so a clip routing had already handed to MediaPlayer was replayed on the engine that had just failed it, burning a whole attempt (watchdog arming, prepare, paint deadline) before the ladder moved on. That was rare while only rotated and aspect-opposite clips reached it and became the common case the moment every non-native aspect became MediaPlayer material. A count rather than a flag so a `.so` failure that was transient rather than deterministic still gets one retry. `lastRoutingAllowedTsPlayer` is written in the same statement that decides it and `tsAttemptsForActiveAsset` is bumped in `startVideoOnController` — the one place an attempt begins, which is why the mid-attempt swap needs no bookkeeping of its own — and both reset at the per-asset `ORIGINAL` edge, on the UI thread with everything else that touches them. `fallbackTsPlayerToMediaPlayer`'s own guard (`videoPlayer != tsPlayerController`) stays as it is: a clip routing handed away has one engine, and its ladder is the same shape an EO1 has always had.
- **Secrets:** Immich password is stored cleartext in device `configuration.json` — never commit a real config

## Config

Device config lives at `/data/data/com.aphex3k.eo1/files/configuration.json`.

- Prefer **`Configuration.java`** as the source of truth for fields.
- `configuration_example.json` is a template for the new multi-backend shape — deliberately listing the `local` entry **first**, because that is the source that needs no server, no credentials and no certificate.

Current model fields: `backends` — a list of `ConfigurationBackendEntry` (`type` "immich"|"local"|"web"|"flickr", `id` like "immich-1"/"local"/"web-1"/"flickr-1", `host`, `userid`, `password`, `apiVersion` = "auto" or a pinned semver, plus `apiKey` and `source` on a **flickr** entry, and `enabled` — **true by default**, and an absent key means true so a config written before the flag existed keeps its backends active; `MediaManager.buildGeneration` skips a false entry and leaves it in the document, so turning a source off is reversible without editing it away. The trusted-network web config editor renders that checkbox for **immich, flickr and web** rows and deliberately renders **none** for a local row (the row reads "local uploads (files stored on this frame - no server, no login)"), because the local store has no failure to gate and no credentials to retire — but `enabled` is still honored on a hand-edited local entry, so it is the field name to know); local entries carry otherwise only `type`/`id`, at most one is honored, and **it must exist**: files uploaded through the web page land in `filesDir/uploaded` and are listed by `/files` whether or not a `local` entry is configured, but nothing joins them to the rotation without one — neither the upload handler nor `Configuration.normalize` creates that entry (normalize only assigns the `id` to a `local` entry already present, and dedupes a second one), and the page's *Add local uploads* button sits inside the trusted-network-gated config editor; a **flickr** entry carries only `type`/`id`/`apiKey`/`source`/`enabled`, ignores `host` entirely (its endpoint is a constant in `FlickrClient`, and `normalize` must not give it the trailing slash it appends for immich), accepts any number of entries, and dedupes by `source` the way web dedupes by URL; see the **Flickr** bullet under **Tech stack**; a **web** entry carries only `type`/`id`/`host` and one entry means one page — `host` holds the page URL verbatim (`normalize` never appends the trailing "/" it adds to an immich base URL), any number of web entries is allowed, and duplicates of the same URL are dropped) — plus `selectedTimeZoneId`, `quietHours` (list of raw 5-field cron expressions, `minute hour day month weekday`; the screen is off whenever **any** expression matches the current minute in `selectedTimeZoneId`, overlaps simply OR), `interval` (minutes between assets; **default 5** per `Configuration.java:44`, and read as `Math.max(1, …)` everywhere, so 0 or a negative value means "as fast as it can go" rather than off), and `autoReboot` (the kiosk watchdog's permission to reboot the device as its last rung; absent/false means it never reboots, and the rungs before it — re-rotate, redraw, repair Wi-Fi, restart the app — are unaffected by the flag; editable in the options dialog and in the trusted-network-gated web config editor). The flat `host`/`userid`/`password` fields are `@Deprecated` legacy: on load, `Configuration.normalize` migrates a legacy flat config into a single immich backend (and re-saves it); on save, `SettingsManager` mirrors the first immich backend back into the flat fields so older APKs can still read the file. The `@Deprecated` `startQuietHour`/`endQuietHour` pair is legacy in the same way: on load it migrates into a single cron expression in `quietHours` (parser: `CronExpression`), and on save a single mirrorable whole-hour window is written back — anything richer degrades to -1/-1 (off, never wrong hours). The **trusted-network** flag is intentionally *not* in `configuration.json`: it lives in the app's default SharedPreferences (key `trusted_network`, off by default, toggled by the *Trusted Network* checkbox in the options dialog) and gates the LAN web server's config endpoints (`/config`, `/config/download`, `/config/import`), which additionally require the per-device **configuration token** as the `token` query parameter (32-hex, lazily generated with `SecureRandom`, persisted under `trusted_network_token`, shown only in the options dialog while the flag is on) — and the two write endpoints enforce a same-origin `Origin`/`Referer` check (see [docs/WEBSERVER.md](docs/WEBSERVER.md)). The **device name** follows the same rule (key `device_name`): it labels one box, so it is kept in SharedPreferences, never serialized into the configuration document, and therefore cannot travel through `/config/download` or `/config/import` and relabel another frame. It is set in the options dialog's **About** tab (which commits on its own button, not on the dialog's Save, because ViewPager2 destroys an off-screen page's views) or by `POST /devicename`; both go through `SettingsManager.setDeviceName`, the only sanitiser, and neither restarts the rotation. Empty means unnamed, and every surface then identifies the frame by platform and IP address alone, exactly as before the field existed. The **backlight level** follows the same rule (key `min_brightness_step`, the opaque step index `BrightnessManager` interprets): it is per-device hardware state, so it is kept in SharedPreferences, never in `configuration.json`, and never exported — importing someone else's config must not silently change how bright this frame is. It is written with `commit()`, not `apply()`, because the frame is routinely power-cycled or crash-exited a moment after the tap and a level that never reached disk comes back as the 0.3 floor on the next boot. Who may change it: on an EO1 the BACK button, and on either frame the web page's `brightness` action (POST-only, because it is the one action whose effect outlives the request) — the step-and-persist path is deliberately not capability-gated, because the EO2 has no button and this value is its only brightness. The **read** is held to the same standard, because "this frame was never adjusted" and "the store would not say" both used to answer `0` — which is also the dimmest step, so one silent failure dimmed the panel and the next tap persisted the dimming as if it had been chosen. `SettingsManager.readMinimumBrightnessStep()` therefore distinguishes `STEP_ABSENT` (the floor is the honest answer) from `STEP_UNREADABLE` (the answer is the last level this process saw on disk — a process-static cache, since `MainActivity.onCreate` rebuilds `SettingsManager` and a re-creation is exactly the event being survived), and `BrightnessManager` records which it got as `stepSource`/`authoritative` in `/state`. A level that was guessed is never grown from: the first step after such a read re-reads the store and steps from what is on disk — but every press still advances the panel, authority cleared or not, because the button is how an operator recovers a dim frame and a store that answers neither way must not be able to freeze it; whether the change outlived the process is the separate `durable` fact. A step outside this build's range clamps to the **nearest end**, not to the floor. And the BACK button's wrap from the top step down to 0.3 stays as it is — it is how a frame comes back down without a second control — so what a "it dimmed by itself" report gets is a record of who moved it (`/state`'s `lastChange`, plus one line in `eo1-app.log`, which survives; logcat holds ~13 minutes), not a removed destination. The **panel hold** is a different fact from the panel level, and a frame that reports one correctly while displaying the other is the report this paragraph exists to answer. `FLAG_KEEP_SCREEN_ON` (plus the `SCREEN_DIM` wake lock that wakes a sleeping panel on the way) is what keeps an always-on display out of the ROM's standby dim, and **while a device sits in that standby state the window's `screenBrightness` does not drive the backlight** — a level written onto an unheld panel is a level nobody sees. So the hold is a *level* the app must go on asserting, never an edge it acts on once: `MainActivity.claimDisplayHold()` is idempotent and is called from `applyCurrentBrightness()` (which every write path already runs through — `onCreate`'s first apply and the rotation tick's included), from `turnScreenOn()`, and from `adjustMinimumBrightness()`, whose own comment has always said a tap is also a wake-up but which previously only flipped a boolean that was usually already `true`; that is how the web page's *Brightness+* could report "fired" and change nothing on the wall. `turnScreenOff()` and `onDestroy()` release it, and the **off** path stays edge-triggered on purpose: it hides the views, cancels an armed video paint watchdog and freezes the kiosk page, none of which is safe to re-run every minute. What this replaced was an assertion reachable only behind a transition — `shouldTheScreenBeOn` starts `true` and `setupQuietHours()` seeds the scheduler's edge memory from the wall clock, so **a process born inside a non-quiet minute never woke the panel and could run for days in the standby dim**: the frame that "resets itself to a dark level" after an app-only restart, on a build whose backlight math is right, whose store is right and whose `/state` says `applied` equals `floor`. `/state`'s `hold` block (`keepScreenOn` read from the live window flags, `wakeLockHeld`, `assertedAtMs`, `repairs`) is the read-back, because `applied` and `screenOn` are both intent; `KioskWatchdog` re-asserts a hold the activity believes it holds, paced by `CLAIM_REPAIR_COOLDOWN_MS`, logged, and earning no rung — an unheld panel keeps rotating, keeps acking, keeps its network, so every age-driven signal about it is honest. Do not gate the claim on `supportsPowerButton()`: that gate on the `ACTION_SCREEN_ON`/`OFF` receiver is why nothing in the app could see an EO1's panel state, and the receiver stays gated only because letting the app's belief follow a hardware wake would override quiet hours.

**MQTT** (options dialog tab **“Media”, “MQTT”, “About”** — `OptionsMqttFragment` / `options_mqtt.xml`): five fields in `Configuration.java` (`mqttHost`, `mqttPort` default 1883, `mqttProtocol`, `mqttUser`, `mqttPassword`; host and protocol are free text — the layout's own hints are `e.g. tcp://192.168.1.155` and “tcp, ssl, ws, etc.” — and `MainActivity` joins them into `protocol://host:port`), also editable in the trusted-network web config editor. What the feature does is narrow and easy to over-read, so state it exactly: `com.aphex3k.eo1.mqtt.MqttManager` builds a Paho client only when `mqttHost` is non-empty, **subscribes to one topic — `sonos/+` — and publishes nothing**, and with no broker named it is never constructed at all. A Sonos coordinator's `transportState` — `MqttManager.PLAY_STATES` (`PLAYING`, `GROUP_PLAYING`) and `STOP_STATES` (`STOPPED`, `PAUSED_PLAYBACK`, `GROUP_STOPPED`, `GROUP_PAUSED`) — drives `MainActivity`'s now-playing banner: title, artist and group name painted over whatever the rotation is currently showing, then faded when the track's own duration elapses. **No MQTT message rotates an asset, installs an update, or reconfigures anything** — there is no command vocabulary on that topic. a broker URI whose scheme begins `ssl` is given the same anchored `SSLSocketFactory` (`ApiServiceGenerator.trustAnchoredSocketFactory`) as the OkHttp clients, so a broker behind a current certificate is reachable from MQTT too (`docs/TRUST.md`); `mqttUser`/`mqttPassword` are credentials and therefore belong to the cleartext-in-`configuration.json` warning above — and an unset one is left **unset on the wire**, never defaulted to a key in the APK (`MqttManager.buildOptions` tests both halves of that).

**Lifetime: the panel owns the connection, not the Activity.** `updateMqttForScreenState()` is called from `turnScreenOn()` and `turnScreenOff()` — the two places every panel decision converges on, not the schedule itself, which is one of four callers — and `onPause()` touches MQTT not at all. That is a deliberate replacement, not a cleanup: the connect used to sit on `startCoreLoop`'s cold-start branch and the disconnect on `onPause`, and because `onPause` deliberately leaves `coreLoopStarted` true, a resume takes the re-arm branch that returns *before* the connect — so the first pause of the Activity ended the session for the rest of the process, on a frame that can sit paused for days. Do not "restore symmetry" by adding a reconnect to `onResume`: with `setAutomaticReconnect(true)` now set, Paho runs its own ladder (`MqttAsyncClient`'s 1 s doubling timer, `maxReconnectDelay` named at 60 s rather than inherited at Paho's 128 s) and an app-side retry would collide with it — a `reconnect()` on a client already reconnecting throws 32110, and on a frame whose broker is simply down it would emit a false alarm forever. `connectionLost` therefore reports and does **not** retry. **What stops the ladder is `MqttManager.stop()`, and it is not `disconnect()`** — that sentence has already been written wrong once in this file's history, so state it precisely: with `automaticReconnect` on, a client whose link dropped sits in Paho's backoff timer in the DISCONNECTED state, and `ClientComms.disconnect()` is guarded on exactly that state, so it throws 32101 *without cancelling the timer*. Quiet hours built on `disconnect()` would therefore have let the frame dial the broker in the dark, which is the opposite of why they close the link. `stop()` disconnects only a live client and otherwise **force-closes** (`ClientComms.close(force)` accepts a DISCONNECTED client, and CLOSED is terminal — every connect path out of it throws 32111, so a timer that fires later has nothing it is allowed to do); and `suspended` is a flag this class owns because Paho offers no way to ask. The client object is **not** rebuilt by a later `connect()` — see the final-paragraph note below: a stopped manager is replaced wholesale, which is why its `client` field is `final`. `/state` reports it, so "down" and "deliberately not dialling" are not the same sentence. Reconcile MQTT from `turnScreenOn()`/`turnScreenOff()`, **not** from `applyScheduledScreenState()` — those two are the chokepoint every panel transition converges on (scheduled, web/button toggle, power-button `reconcileScreenState`, brightness adjust), and hooking only the schedule left a frame deaf after a `Brightness+` wake following quiet hours. A cleared `mqttHost` is its own case in `connectMqttIfConfigured()`, before the address-change test: with nothing configured there is no address to differ from, so a change-only check leaves the client dialling a broker the operator removed. **That case must not leave `mqttManager` null in a way the next panel-on cannot repair** — restoring the host has to rebuild the manager, so `updateMqttForScreenState()` tests only `brightnessManager` for null and lets `connectMqttIfConfigured()` construct what is missing; a `mqttManager == null` early return anywhere above the rebuild makes MQTT dead until the Activity happens to be recreated. Inside `stop()`, `close(true)` is in a **`finally`**, not in an `else` beside the `isConnected()` test: the link can drop between that test and `disconnect()`, and a `disconnect()` that then throws leaves the ladder running on an object nobody holds — which with a stable id evicts its successor. Close also covers the clean path, where a successful disconnect still leaves Paho's threads and persistence allocated. **`connect()`/`disconnect()` are blocking calls (`MqttClient`), and they never run on the caller's thread: every one of them is queued on `mqttExec()`, a single daemon serial worker in `MainActivity` whose tasks are each wrapped against `Throwable`.** That became necessary when the reconcile moved onto `turnScreenOn()` — the panel-wake path is reached from key dispatch (`EventManager.onKeyDown` → `adjustMinimumBrightness` → `turnScreenOn`), so a broker that was merely unreachable would have stalled the input thread past Android's ~5 s dispatch timeout and gotten the process ANR'd, which is the signal `KioskWatchdog` escalates on, over a now-playing banner. One serial queue rather than a thread per call also preserves order: a dial queued before a quiet-hours stop still finishes before it, so the panel going dark cannot be overtaken by its own connect. `onDestroy()` queues its `closeQuietly()` and then `shutdown()` — not `shutdownNow()` — so an already-queued connect drains ahead of the stop instead of landing after it and leaving a reconnecting client owned by nobody. That shutdown sits **outside** the `mqttManager != null` guard, because a frame whose host had already been cleared reaches `onDestroy()` with the manager null and would otherwise leak the idle worker on every recreation.

**Retiring a manager publishes the new field value before the teardown is queued** (`retireMqttManager()`), and every path that drops one goes through it — quiet hours, a cleared `mqttHost`, a changed broker address. Order matters here in a way a glance misses: `stop()` runs whenever the worker reaches it, so if `mqttManager` still named that client, an off→on transition landing before the queue drains would consult a manager that is still unsuspended and still connected, skip the dial as unnecessary, and then be suspended by the stop sitting behind it — MQTT held with the panel lit, until something else reconciled it. Clearing the field first makes that wake build a fresh manager whose dial queues behind the stop rather than racing it. `mqttHeldForPanel` is what `/state` uses to tell "quiet hours" from "never configured", since a retired manager is null either way. An uncaught throw on any thread in this app reaches the one global `UncaughtExceptionHandler`, which calls `System.exit(2)`, so the wrapping is not optional. Bounding the calls themselves still needs two settings, not one. `connectionTimeout` covers the socket and the CONNECT exchange; it does **not** bound the wait that actually blocks the caller. `MqttClient.connect()` finishes with `token.waitForCompletion(getTimeToWait())`, and `MqttClient.<init>` stores `timeToWait = -1` — infinite — so a broker that accepts the TCP connection and never answers CONNACK holds the frame's main looper forever, with `connectionTimeout` set and looking correct. `client.setTimeToWait(PROTOCOL_WAIT_MS)` is therefore called on every client this class builds (15 s, above the 10 s connect timeout so the protocol timeout is what normally fires), and it bounds `subscribe()`'s SUBACK wait through the same field. A stall on the main looper is what `KioskWatchdog` measures through `mainLoopAckAtMs`, and a decorative feature must never be able to walk a frame up the ladder. The disconnect quiesce is 1 s.

**One `MqttClient` per `MqttManager`, final, never swapped.** A stopped manager is *replaced*, not revived — `connect()` on one throws 32111 and `connectMqttIfConfigured()` rebuilds it when `isSuspended()`. This is what closes the stale-callback race rather than checking for it: Paho cannot re-open a closed client, so a field that swaps to a successor while an old client's `connectComplete` is in flight would have that callback force-close the client that just replaced it, leaving a closed, non-null object that no later `connect()` rebuilds — MQTT dead until a reboot. Binding callbacks to a generation number would be the alternative; keeping the object immutable makes the question unaskable. `MqttSuspendTest` pins the refusal.

**Every callback in `MqttManager` must be incapable of throwing.** This is the contract, not a style rule: `CommsCallback` dispatches `messageArrived`, `connectionLost` and `connectComplete` inside one `catch (Throwable)` whose handler calls `ClientComms.shutdownConnection()`, so a single exception out of any of them closes the socket **without** a DISCONNECT packet — which is what "the frame keeps disconnecting" looked like from mosquitto, via `gson.fromJson("", Payload.class)` returning null two lines before the null check that would have caught it. The guard is `if (payloadObj != null …)` *before* any `transportState` dereference, plus a `catch (Throwable)` around the listener call, and `MqttPoisonMessageTest` feeds every shape that ever reached it. **Every executable statement in that method lives inside a `catch (Throwable)`, including the ones that look incapable of throwing** — a `String.trim()` sitting outside a guard was a live disconnect risk, because it allocates a copy whenever a payload is whitespace-padded and an `OutOfMemoryError` on a heap this size escapes through Paho's own handler. The body-shape test therefore scans with `length()`/`charAt()`/`isWhitespace()` instead of trimming: no allocation, and padding still reaches Gson (`aPaddedStatePayloadStillDrawsABanner`), which is the behaviour `trim()` was there for. Adding a fourth `try` would have passed review too; removing the allocation is the version that cannot be re-broken by the next statement someone writes outside a guard. QoS is **0** for the same reason: this is state, the next publish supersedes anything missed, and a QoS 1 message is only acked once `messageArrived` returns, so an unreadable payload became a standing redelivery. Do not move a `subscribe()` back into `connect()`: `ConnectActionListener.onSuccess` dispatches `connectComplete(reconnect=false, …)` for the first session too (checked at bytecode), so `connectComplete` is the single place the subscription is issued — and it has to be, because **Paho 1.2.5 contains no resubscribe code at all** (no class in the jar spells the word) and `cleanSession=true` means the broker forgot the filter. A reconnect that skipped the re-subscribe is a frame reporting itself connected and deaf, which is indistinguishable from this bug.

**The client id is stable, per-frame state.** `SettingsManager.mqttClientId()` mints `"eo1-"` + 16 hex from `SecureRandom` once and persists it under `mqtt_client_id` with **`commit()`** — like `min_brightness_step`, because these frames are power-cycled moments after a write and an id that never reached disk comes back as a *second* minted value. It is never in `configuration.json` and never exported: an id that travelled through `/config/download`/`/config/import` would put two boxes on one broker under one client id, and MQTT answers that by closing the older connection, so the pair kick each other off in a loop. If the store will not answer, `MainActivity` falls back to `MqttClient.generateClientId()` — "this frame is anonymous" is a degraded answer, "MQTT cannot start" is not (Paho rejects an empty id outright). Reading the broker log correctly still needs one rule: `generateClientId` was fixed at construction and the only `new MqttManager` was in `onCreate`, so **a fresh `pahoXXXX` in a log means a new object, i.e. a process start or an Activity recreation** — a symptom to read, not a defect to fix. `connect()` guards on `isConnected()` because `settingsChanged()` already falls through to a connect on a live client and Paho answers with 32100; a broker address change instead `closeQuietly()`s and rebuilds, since the URI is fixed inside Paho at construction. `closeQuietly()` puts `close()` in a `finally` — nothing in this repo ever called `close()` before, so every recreation abandoned a live client, which with `automaticReconnect` on would then reconnect under the same id and evict its successor.

Two things that made a broker message able to reboot a frame are closed: `MainActivity`'s `onPlaybackStarted` now returns on a `PLAYING` with no `currentTrack` (the read was unguarded, unlike the `STOPPED` path, and it ran inside `runOnUiThread`, so it reached `CrashReporter` → `System.exit(2)`), and `onPlaybackStopped` compares with `trackId.equals(currentTrackId)` because `currentTrackId` is null until the first banner. `GROUP_PLAYING` is now its own literal — it was the string `"PLAYING"`, which made `PLAY_STATES` a two-element array holding one value, so a group coordinator reporting `GROUP_PLAYING` never drew a banner. Reporting goes through `MqttManager.Reporter` (an app-defined interface, for API 19) into `Log` + `debugInformationProvided`, and `/state` carries an `mqtt` block (`connected`, `uri`, `clientId`, attempts, reconnects, `lastMessageAtMs`, `lastError`) plus one `mqtt :` line in the durable dump — because the six `System.out`/`System.err` calls this replaced are the only stdout in product source, they land in logcat's **main** buffer, `CrashSources` scrapes `-b system`, and `config.mqttHost` reported only what was *set*, never what was dialled or alive.

### Refreshing the shipped CA roots

Nothing about this runs on its own, and it should not: it changes what every frame will accept as a
certificate chain.

```bash
./update-roots.sh --dry-run --suite sid   # fetch, verify, prune expired, print adds/removes, write nothing
./update-roots.sh --suite sid             # write certs/roots/*.pem, MANIFEST.tsv, debian.json, RootBundle.java
./publish-update.sh --check-only          # the release's own gate, without building
```

Read `git diff certs/roots/MANIFEST.tsv` before committing — removals are the lines that change behaviour,
and they are printed under `REMOVED` for the same reason. `./gen-root-bundle.sh` alone only re-derives
`RootBundle.java` from whatever is already in `certs/roots/`.

### GitHub dependency reporting

`.github/workflows/dependency-submission.yml` (on push to `main` + manual) resolves the `:app` classpaths with Gradle (no tests, no packaging) and submits a dependency snapshot to the GitHub dependency graph (`POST /repos/…/dependency-graph/snapshots`). Local preview:

```bash
./gradlew :app:dependencySubmissionSnapshot   # writes app/build/dependency-submission-snapshot.json
```

The Gradle wrapper jar is deliberately a regular git object, not LFS: this repo is a GitHub fork and cannot serve its own LFS objects, so a plain checkout would leave the wrapper as an LFS pointer and `./gradlew` could not start in Actions. The blanket `*.jar` LFS rule in `.gitattributes` is overridden for it — keep it that way.

Device install (EO1 browser sideload vs EO2 `adb`) is documented in [README.md](README.md) — not required for most code changes.

### Dependabot & the API-19 ceiling

`.github/dependabot.yml` turns on Dependabot **version updates** (gradle + github-actions, weekly).
Because this app is pinned to `minSdk`/`targetSdk`/`maxSdk` = 19, Dependabot must never open a PR that
raises a dependency above the last release that installs on KitKat — Dependabot reads no manifest SDK
field, so every ceiling is hand-authored in the file's `ignore` blocks. **`ignore` gates BOTH the
version and the security path for gradle** (`gradle/update_checker/version_finder.rb` calls
`filter_ignored_versions` on both), and there is no `applies-to` under `ignore` — so a ceiling is
unconditional, which is exactly what satisfies "never suggest past the ceiling," and is why an
advisory fixed only above a ceiling becomes a permanent alert with no PR (see the register).
Authoring rules: a bare `versions: ["X"]` is **equality** (ignores one release, silently dissolving the
ceiling — always use an operator), and prefer `> <last known good>` over `>= <first known bad>` so the
next line's already-published alphas are caught. Keep this table and the yaml in sync.

## Do / don’t

**Do**

- Keep API 19 compatibility and existing Retrofit/OkHttp pin strategy
- On a breaking Immich API change, add a new frozen `com.aphex3k.immichApi.vN` DTO package + `ImmichClientVN` + a registry band in `com.aphex3k.media.immich.ImmichClientRegistry` — never edit a frozen client package
- Treat `app/src/main/java/com/aphex3k/eo1/` as the app core and `com.aphex3k.media` as the backend layer (per-backend client wiring; `MediaManager` only orchestrates)
- Gate platform-specific hardware behavior (soft-touch buttons, light sensor, screen brightness, power button) on `HardwareCapabilities` flags — never add model-specific `if`s on `Build.MODEL`/`Build.DEVICE` elsewhere; unsupported features no-op. Gate the **input device**, not the **capability**: `supportsBrightnessButton()` says whether a frame has a key that asks for a brighter floor, `supportsScreenBrightness()` says whether its panel accepts a brightness value (true on both — the window attribute is not platform-specific). Gating a *feature* on the button flag is how the EO2's brightness floor became unreachable by anything, since that frame has no button and its floor is the only brightness it has
- Keep the LAN web server dependency-free and resource-cheap (hand-rolled `ServerSocket`, `Connection: close`); every web-server thread must be defensively wrapped — a stray exception must never reach the global `UncaughtExceptionHandler` (which calls `System.exit(2)`)
- Write crash-path stack traces by walking the cause chain **iteratively** (`CrashStore.printTrace`), never `Throwable.printStackTrace`: that recurses once per cause, so a deep chain raises `StackOverflowError` on the dying thread — where the stack is already the suspect — and the whole report is lost. Also note `PrintWriter` has no `Throwable` overload, so `pw.print(error)` compiles to `print(Object)` and writes `toString()` only
- Let `libTsPlayer-jni.so` loop a media file **natively** — create the TsPlayer once per asset and run no per-duration Java teardown loop; full `deletePlayer` + `createPlayer` only on asset handoff / `stop()` / `surfaceDestroyed` (see [docs/TSPLAYER.md](docs/TSPLAYER.md) “Looping (native)”)
- Keep every adbd command line built from fixed constants — the install path (`AdbdInstallClient`, staged public-copy path only), the `service.adb.tcp.port` / `ctl.restart` writes in `ensureTcpAdbd`, and the `DeviceRepair` ladder (`svc wifi disable`/`svc wifi enable`, `reboot`, and the `pm disable com.geniatech.upgrade` / `pm disable com.electricobjects.updater/.{CheckUpdateReceiver,BootCompletedReceiver}` lines it runs once from `MainActivity.onCreate`) alike; never interpolate user/config/network input
- In `VendorPollers`, read a poller's **package** setting first and its components only as an OR after it: `getCurrentEnabledStateLPr` consults nothing but the component sets, so every component of a package disabled at package level answers `DEFAULT`, and a components-only check would report a correctly silenced frame as armed and force-stop a system-uid package on every launch. An unreadable read is `UNVERIFIABLE` (fall through to writing), never `QUIET`
- Let the kiosk watchdog escalate only *down* its ladder (rotation → redraw → network repair → self-restart → opt-in reboot), one rung per wedge, with the device reboot kept behind the options-dialog permission — an unattended frame should self-heal, but not silently hard-reboot in a loop

**Don’t**

- Ship, default to, or fall back to any credential of the app's own. Every backend takes its credentials
  from the operator and nobody else, for any service, always; an entry missing one is *not configured*
  (invalid, skipped, setup dialog), never "use ours". A built-in key is one shared blast radius across the
  whole fleet — one revocation, one throttle, and it is the shape that produced issue #94's "only 3-4
  frames work at a time".
- Treat a backend's terms of use as a risk to document rather than a requirement to meet. Where a clause
  needs a channel the product does not have (Flickr's 24-hour removal request), build the channel:

Its body may not throw and may not chain to the framework handler: the +120 s relaunch alarm and `System.exit(2)` are the contract `KioskWatchdog` and `UpdateManager` depend on, so they belong in a `finally` that a failed report write still reaches
- Where the app spawns a subprocess (`CrashSources` → `logcat -d -b system`), use `ProcessBuilder`/`Runtime.exec` with an **array** argv, an absolute binary path, and a compile-time constant — never the single-string form, never a directory listing or any value interpolated. Bound it by elapsed time *and* byte count and `destroy()` it: `Process.waitFor(long, TimeUnit)` does not exist before API 26, and a bare `waitFor()` before draining stdout can hang the thread forever. **Read the exit status**: stderr is merged into the stream we drain, so a rejected command otherwise looks like a successful capture of nothing. **Reap before you signal, and never wait ON the child.** `destroy()` is a no-op only on a process that has already exited, so signalling first puts a signal number in the status and the exit-status gate then condemns a capture it read in full (an EO2 log said `logcat exited 9` for a scrape that worked). And because `Process.waitFor(long, TimeUnit)` does not exist before API 26, a `waitFor()` that follows the read is unbounded: a child that closes stdout and then lingers parks the reaper forever and the `destroy()` below it becomes unreachable, which is how one revision of this code leaked the child it existed to reap. Observe with `exitValue()` inside a window that closes **before** the caller's bound, then destroy unconditionally — a post-reap destroy cannot alter the status, so the no-leak guarantee stops depending on which line execution happens to reach. **And let exactly one thread own `destroy()`/`waitFor()` for the life of the child** — `java.lang.UNIXProcess` hands the exit status to the first waiter and can leave a second waiting for a notification already delivered, so a reader that reaps in its own `finally` beside a deadline helper that is still inside `destroy()` parks the startup scrape forever, on a frame with nothing wrong with it. `CrashSources.drain()` is shaped as reader + reaper + one monitor for that reason, and the scrape thread that got stuck there was the whole of a bug that took a trace dump to look like. Two more consequences of the same drain: read **to EOF** and let the byte cap bound what is *kept*, never what is *seen* (a `system` buffer larger than `MAX_OUTPUT_CHARS` is a source that worked and was partly read — stopping the scan at the cap made every frame with real uptime report `unavailable` and discard the crash lines already filtered), and a non-zero exit **because we ended the child at the deadline** is a successful partial read, not the `exit != 0` path that exists to keep a refused `logcat` from being stored as the crash it never read. **A termination flag must not overwrite a recorded error.** When the reaper kills a child that will not exit it marks the run terminated so the partial capture survives rather than being judged by the signal it received — but that stamp belongs only where no read error is on the record (`weKilled && d.error == null`). The terminated branch deliberately skips the read-error check, so stamping it over a failure the reader reported on its own turns a source that was never read into `empty`, which reads to an operator as "no crash in the buffer"
